# 第 16 章 · 确定性与可复现性专题

分布式通信库的"确定性"指：相同输入、相同配置下，通信的数值结果逐位相同。这看似是个小需求，实际上触及 DeepEP 的大部分协议设计——路由的排序、槽位的分配、归约的顺序、句柄的复用。本章把这些散落在前文的确定性相关机制收拢成一个完整的专题：什么影响确定性、DeepEP 提供了什么、代价是什么、如何验证。

## 16.1 确定性的三个来源层次

一次 EP 通信的数值结果由三个层次的决策共同决定，每一层都有确定与非确定两种可能：

**第一层：路由决策。** 哪个 token 被发给哪个专家，由门控（gate）决定。这发生在 DeepEP 之外（第 7 章"机制在库、策略在用户"），通信库对它无能为力——若门控本身含随机性（dropout 式路由、随机 tie-breaking），整个系统不可复现。集成方要在框架层保证门控确定，例如 `deep_ep/utils/envs.py` 提供的种子体系（全局种子派生本地种子的机制，配合多进程训练的每 rank 种子管理）。

**第二层：布局与槽位分配。** 给定路由，token 在接收缓冲中的位置由"计数 → 前缀和 → 槽位"决定（第 4 章）。这一层在 DeepEP 内部，且其结构天然偏向确定：计数是原子加的**和**（加法交换律保证与到达顺序无关），前缀和是计数的确定性函数，槽位由前缀和唯一决定。唯一的非确定风险在"同 token 多专家槽的排序"上——展开式布局里同一 token 的 $k$ 份贡献按什么次序排列，需要有固定的规则。

**第三层：归约顺序。** combine 的求和（以及 bucket 的归约）是浮点加法，交换但不结合——顺序不同则结果可能差一位尾数。多重归约的途中合并顺序取决于通道与到达时序（第 5.10 节），是天然非确定的；单次归约把所有加法收敛到接收端 epilogue 的固定顺序，是可确定的。

DeepEP 的应对是把第二、三层做成显式可配置：构造参数 `deterministic`（EPBuffer）与 `EPHandle.deterministic_sort`（`deep_ep/buffers/ep.py` 中定义于 EPHandle 上的确定性排序方法），配合运行时检查 `check_torch_deterministic()`（每次 dispatch/combine 前调用，校验 PyTorch 全局确定性模式与 DeepEP 确定性实现的兼容性，第 4 章）。

## 16.2 参考语义：确定性的判据

确定性需要一个"规范答案"作为判据，DeepEP 的判据是参考实现 `deep_ep/utils/refs.py`：其 dispatch 输出"Not expanded. Sorted by rank and then by token within each rank (i.e. sorted by `src_token_global_idx`)"，越界的 `recv_topk_idx` 置 -1。这句话定义了两件事：**布局的规范顺序**（先按来源 rank、rank 内按来源 token 全局编号）与**边界语义**（未选中的槽位如何表示）。`src_token_global_idx = src_rank_idx * num_max_tokens_per_rank + src_token_local_idx` 这个公式同时说明：容量参数 `num_max_tokens_per_rank` 参与了"全局编号"的定义，因此它是"所有 rank 必须一致"的参数之一（README）——不一致不仅破坏缓冲区大小对称（第 3 章），还会破坏参考语义中全局编号的唯一性。

测试体系（第 12 章）把参考语义变成可执行的判据：`tests/ep/test_ep.py` 以受控负载（`tests/utils/test_gate.py` 的 `generate_rank_count`/`generate_topk_idx`，按 ratio 参数生成均衡到极端倾斜的确定性负载分布）驱动内核，用 `calc_diff` 与参考实现比对。确定性模式的验证则更进一步：同一输入跑两遍、逐位比较。集成方建立自己的回归测试时，应当沿用这个"受控负载 + 参考语义 + 逐位对比"的三件套。

## 16.3 确定性模式的能力边界

需要诚实地划清确定性模式"能保证什么、不保证什么"：

**能保证**：给定确定的路由输入，通信输出（`recv_x`、`recv_topk_idx`、`recv_topk_weights`、combine 结果）逐位确定。机制是：确定性排序固定同 token 多专家槽的次序；单次归约（配合关闭 `allow_multiple_reduction`，第 5 章）固定求和顺序；槽位分配本身是计数的确定函数。

**不保证**：门控决策的确定性（框架层责任）；跨进程浮点环境的位级一致（不同 SM 数、不同内核特化可能产生不同展开顺序——这也是为什么确定性模式下的配置应当全组一致并固定 `num_sms`，避免每次调用的运行参数漂移）；以及非浮点的事件时序（通信完成时刻显然是调度相关的，确定性只针对数值）。

**代价**：确定性排序与单次归约都有性能成本——排序增加一次规整化步骤，单次归约放弃了途中合并的传输节省（第 5 章 `use_rank_layout` 仅在 $k \ge P$ 时省流量的机会也随之让渡）。README 把 `allow_multiple_reduction=False` 描述为"only one reduction will be done in the combine epilogue for best precision"——精度最优与确定性最优在此重合，这是浮点加法"顺序决定结果"性质的直接推论。

## 16.4 与调度非确定性的关系：重叠模式的可复现性

一个容易被忽略的事实：即使数值确定，**通信与计算重叠的调度也是非确定的**——独立计算与通信内核的交错由硬件调度决定。这对训练的影响为零（重叠只影响时间不影响数值，因为 epilogue 的数学在等待点才执行，第 5 章），但对"复现某次运行的耗时"类调查有影响。DeepEP 的机制在此提供了一个有用的分隔：`EventOverlap` 的 `current_stream_wait` 是数值的分界点（epilogue 在此执行、结果从此产生），时间的分界点是各流的事件对齐。做耗时复现调查时，应当固定重叠配方（第 13.5 节三选一）并关闭剖析干扰（`EP_USE_NVIDIA_TOOLS` 与 `EP_DISABLE_BARRIER_PROFILING` 的剖析行为，README 明确它们只影响 `bench_kineto` 的报告）。

## 16.5 逐位确定性的实践配方

把前文机制拼成一个可操作的"逐位可复现"配方：第一，框架层固定门控（固定种子、避免随机路由），并让所有 rank 的种子体系经 `envs.py` 的全局/本地种子机制一致派生；第二，构造 `EPBuffer` 时 `deterministic=True`，并在每次 dispatch/combine 前保持 `check_torch_deterministic()` 所要求的 PyTorch 环境一致（不与框架的全局确定性设置冲突）；第三，关闭 `allow_multiple_reduction`（单次归约）；第四，固定 `num_sms`/`num_qps` 为显式值（避免估算值随探测波动，虽然估算被缓存，但跨进程重建缓冲区时输入可能变化）；第五，所有 rank 使用完全一致的构造参数与容量（`num_max_tokens_per_rank`、`expert_alignment`、`use_fp8_dispatch`）；第六，句柄复用时保证 `topk_idx` 只读（第 4 章不变式）。六个条件缺一不可——前五个决定"每次计算"确定，第六个决定"跨次重放"一致。

对于只要求"统计可复现"（损失曲线一致、指标方差可接受）而不要求逐位一致的场景，可以保留默认配置（多重归约开启、估算 SM 数），只做第一、五、六项——这是绝大多数训练框架的实际需求，性能代价也最小。

## 16.6 确定性与负载均衡原语的关系

第 7 章的 EPLB 原语在确定性视角下有一个特殊优势：`redundancy_mapping` 是**静态已知的贡献图**——谁复制谁、谁贡献给谁，在调用前就完全确定（域内一致的映射表）。因此 `lb_reduce_grads` 的归约顺序由映射表决定，天然确定；这与 combine 的动态路由归约（顺序取决于运行时通道与到达）形成对照。集成方若在梯度链上要求逐位确定，应优先依赖 EPLB 链路的静态性，并对 combine 链路应用 16.5 节配方。反过来，动态复制的**规划**本身（哪些专家热点、复制几份）依赖运行时负载统计（`cumulative_local_expert_recv_stats`，第 4 章），统计的采样窗口与规划时机由调用方决定——规划器要成为确定性的，同样需要确定性的输入。

## 16.7 本章小结

确定性贯穿 DeepEP 的三层决策：路由（框架层责任，通信库不覆盖）、布局与槽位（结构上偏向确定，确定性排序补齐最后的不确定点）、归约顺序（多重归约非确定、单次归约可确定）。判据是 `refs.py` 的参考语义（排序规则 + `-1` 边界 + 全局编号公式），验证是"受控负载 + 参考对照 + 逐位对比"三件套，代价是排序与单次归约的性能让渡。逐位可复现的完整配方是六项条件的合取（确定门控、确定性模式、关闭多重归约、固定运行参数、一致构造、句柄只读纪律）；统计可复现的最小配方只需三项。EPLB 链路的静态贡献图使其天然比 combine 链路更易确定——这个不对称值得集成方在设计回归测试时利用。

## 16.8 延伸讨论：加法结合律与归约树的数学

本节把"为什么顺序影响浮点和"从直觉升级为可计算的事实，为确定性代价的量化提供基础。浮点加法不满足结合律：$(a+b)+c$ 与 $a+(b+c)$ 的结果可能差一位尾数，原因是每次加法都要对齐指数并舍入——中间结果越大，对齐时被舍掉的低位越多。把这个性质放到 $n$ 输入的求和上：不同求和树（串行链、二叉树、多路并行）的最大中间结果与舍入次数不同，其结果差异的上界由树的深度与输入的模长分布决定（第 15.9 节的抵消区效应叠加其上）。多重归约相当于允许求和树在"途中"分叉与合并（合并点取决于运行时通道与到达时序），等价于在树族中随机选树——这就是它位级不可复现的数学本质；单次归约把树固定为"接收端 epilogue 的固定循环"，等价于固定一棵树。由此可以给出确定性代价的精确表述：关闭多重归约的传输代价是放弃合并率 $\mu$（第 5.11 节），数值收益是求和树确定。有趣的是，确定树不一定是"最准"的树——配对求和（pairwise summation）在实践中误差更小，但 DeepEP 的选择标准是可复现而非最优树形，因为"可复现"是训练工程的可验证属性而"最优树形"是每次运行都变的不可验证属性。这个取舍与第 20.3 节"确定性优于适应性"的方法论一致。

## 16.9 延伸讨论：框架协同的种子管理

第 16.5 节把门控确定性列为框架层责任，本节说明 `deep_ep/utils/envs.py` 的种子体系如何配合这一责任。该模块维护全局种子与本地种子（`_global_seed`、`_local_seed`，第 2 章模块表）的关系：全局种子由用户设定，本地种子由全局种子派生——派生的意义在于多 rank 并行时每个进程需要一个"既与全局相关、又彼此不同"的随机流（数据增强、路由扰动等框架侧随机性），直接用同一全局种子会让所有 rank 的随机序列相同（数据重复），直接用各自随意种子则破坏可复现性。派生机制让"从全局种子重放整个训练"成为可能：固定全局种子后，每个 rank 的本地种子是其确定函数，门控侧的随机决策（若有）也纳入这个体系即可被重放。集成方的接入点：训练框架在初始化时调用 envs 的种子设置（并让 DeepEP 的确定性模式与 PyTorch 全局确定性通过 `check_torch_deterministic` 的校验，第 16.1 节），之后所有随机源——框架的、门控的、测试的 `generate_rank_count`——都从这条种子链取随机数。值得强调的是边界：种子链保证的是"决策可重放"，而 DeepEP 保证的是"决策的通信结果逐位确定"，两者合起来才是端到端可复现；缺了前者，通信层再确定也只是在重放不同的路由。

## 16.10 延伸讨论：确定性问题本身的调试方法

当怀疑"确定性没生效"时，本节给出一套定位顺序。第一步，定义对照物：位级对比需要固定两次运行的一切输入（同一检查点、同一数据顺序、同一受控负载），任何框架层的非确定（ dropout、数据乱序）都会污染对比——先用最小配置（单层、小批次、受控 gate 负载，第 12 章三件套）建立干净对照。第二步，分层二分：对比 dispatch 输出（`recv_x` 与参考实现）确定非确定发生在路由层还是通信层；若 dispatch 输出逐位一致而 combine 不一致，问题在归约顺序（检查 `allow_multiple_reduction` 是否真的关闭、构造参数是否全组一致，第 16.5 节第三、五项）。第三步，配置审计：六项配方逐项验证，最常见的"漏项"是第二项（PyTorch 全局确定性模式未开或与 `check_torch_deterministic` 冲突）与第四项（SM 数走了估算而探测输入有波动，第 16.5 节）。第四步，环境审计：不同 GPU 代次、不同 JIT 缓存产物（内核特化不同）之间的位级一致本来就不该假设（第 16.3 节"不保证"清单），对比必须在同构环境内进行。这套顺序与第 14.10 节性能归因法同构（先便宜后昂贵、先环境后代码），是"确定性"与"排障"两个专题的合流点。

## 16.11 延伸讨论：确定性与性能的量化权衡实验

第 16.3 节指出确定性模式有性能代价，本节设计一个最小实验把代价量化，让集成方可以用自己的负载回答"值得吗"。实验矩阵：同一负载（受控 gate 负载，规模取训练峰值）跑四种配置——基线（默认参数）、关闭多重归约、开启确定性模式（`deterministic=True`）、两者都开；每种配置记录三层指标——端到端层时间、dispatch/combine 内核时间（`bench_kineto` 的内核级解析，第 12 章）、以及传输量估算（第 1 章公式乘上配置差异）。预期结果的解读框架：关闭多重归约的代价集中在 combine 的传输量（$k \ge P$ 时合并收益消失，第 5.11 节），在 RDMA 主导的配置下代价显著、在 NVLink 主导下可能被带宽余量吸收；确定性排序的代价集中在内核内的额外规整步骤（小批次下占比更高）；两者的叠加通常小于之和（排序避免了部分重复整理）。实验的输出是一张"确定性税"表——按批次规模列出各配置的净代价——集成方据此选择：训练主循环用统计可复现的最小配方（第 16.5 节），损失审计与回归对比时切换到完整配方并接受该表的代价。这个实验也再次展示了第 13.1 节的方法论：每个开关的代价都可以被测量并写成数字，而不是停留在"确定性会慢一点"的印象。

## 16.12 延伸讨论：可复现性的分层目标与验收

作为确定性专题的收口，本节给出可复现性的分层目标体系，避免"一刀切"的过度承诺。第一层是**决策可重放**：种子链（第 16.9 节）保证门控与框架随机性可重放——这是成本最低、收益最大的一层，任何训练系统都应达到。第二层是**通信数值确定**：第 16.5 节最小配方——在默认配置下通信输出的统计性质稳定、单次运行的数值可信赖，满足绝大多数训练监控需求。第三层是**端到端位级可复现**：完整配方（六项）加同构环境——成本最高，仅在需要"逐位对比两次运行"的场景启用（损失异常审计、内核回归验证）。第四层是**跨环境可复现**：不同 GPU 代次、不同内核特化之间的位级一致——DeepEP 明确不承诺（第 16.3 节），集成方不应以此为验收标准。分层体系的验收方式：第一层用"重放若干步后路由分布一致"验收，第二层用"指标曲线方差在阈值内"验收，第三层用第 16.10 节的对照流程验收。把第 16 章的机制映射到这个分层上，读者可以为自己的项目画出"需要哪几层"的决策线——通常答案是一、二层常开，第三层按需开关，第四层永不依赖。

## 16.13 延伸讨论：位级复现的验收脚本设计

第 16.10 节给了确定性的调试顺序，本节把它固化为一个可执行的验收脚本设计——当第三层（端到端位级复现）是团队需求时，验收应当自动化而不是手工对照。脚本的结构分四段。第一段，环境固定：记录并断言两次运行的配置完全一致（构造参数、`num_sms`/`num_qps` 显式值、JIT 缓存指纹、种子链状态，第 16.5 节配方的前五项），任何一项不一致直接判"环境无效"而非"非确定"。第二段，负载固定：使用 `generate_rank_count`/`generate_topk_idx` 的受控负载并以固定种子生成两份完全相同的输入（第 12 章三件套），保证路由决策逐位一致——这是配方的第一项（确定门控）的机械实现。第三段，双跑与逐位比对：同一输入跑两遍 dispatch/combine，对输出张量做逐字节相等断言（不是 `calc_diff` 容差——位级复现的验收标准是零差异，第 16.3 节），任何一位不同则收集差异位置的分位数定位偏差模式（集中在归约输出还是路由索引）。第四段，跨进程扩展：把双跑扩展为"同配置重跑进程"（进程退出再进，验证 JIT 缓存与估算缓存的重放一致性，第 11.10 节、第 16.5 节第四项），这一段能暴露"单进程内确定、跨进程不确定"的缓存漂移问题。脚本的价值是把第 16.5 节的六项配方变成可持续执行的回归防线——确定性不是配置一次就一劳永逸的属性，内核升级、配置调整都可能悄悄破坏它，自动化验收是唯一的保险。

## 16.14 延伸讨论：确定性与故障恢复的关系

确定性与容错（训练中断后的恢复）有一条容易被误解的关系，本节把它辨析清楚。误解是"确定性使断点恢复更容易"——实际上两者是正交的机制。断点恢复的正确性依赖的是**状态持久化的完整性**：优化器状态、梯度累积的中间值、数据加载位置、以及 EPLB 的映射表与冗余梯度状态（若在恢复窗口内活跃，第 7 章生命周期纪律）都要在检查点里。确定性提供的是另一个性质：恢复后重放的步骤与中断前的步骤产生相同的数值——这要求恢复时的配置与中断前一致（第 16.5 节第五项），且种子链按恢复步重派（第 16.9 节）。两者的交点只有一个：确定性让"恢复后数值与前一次运行相同"成为可能，从而支持恢复后的行为验证（对比恢复前后的损失与梯度范数，第 15.13 节模板第五格）。反过来说，非确定配置下的恢复同样正确（恢复后的运行是一个新的合法轨迹），只是无法与前次轨迹逐位比较。集成方的结论：不要为了恢复而开启完整确定性配方（代价见第 16.11 节），恢复的正确性靠检查点纪律；确定性配方只在需要"恢复后行为验证"的场景切换启用。这个辨析与第 16.12 节分层目标呼应：恢复属于运行正确性（第一、二层的范畴），位级对比属于审计能力（第三层的范畴）。

## 16.15 延伸讨论：确定性契约的文档化建议

本章反复出现的六项配方、分层目标与验收脚本，最终应沉淀为一份"确定性契约"文档——它是对外承诺（框架向用户、平台向租户）与内部检查（评审与验收）的共同依据。契约建议包含五节。第一节，承诺层级：明确声明支持第 16.12 节的哪几层（多数训练框架声明第一、二层），以及不承诺什么（第四层跨环境位级一致，第 16.3 节）。第二节，启用方式：每层的开关清单与配置差异（默认配置、最小配方、完整配方的具体参数值），并注明代价引用（第 16.11 节的"确定性税"表）。第三节，判据与验收：参考语义的引用（`refs.py` 的排序规则与 `-1` 边界，第 16.2 节）、验收脚本的运行方式（第 16.13 节四段结构）、容差与零差异的适用范围区分（`calc_diff` 用于统计层，逐字节相等仅用于位级层）。第四节，边界与免责：门控决策在框架层（第 16.1 节）、跨环境一致性不承诺、确定性模式与 PyTorch 全局确定性模式的兼容条件（`check_torch_deterministic` 的校验语义）。第五节，变更流程：任何影响确定性路径的变更（归约布局默认值、排序实现、量化方案）必须走契约评审并重跑第三节的验收——把第 15.15 节的回归触发条件在确定性维度再覆盖一遍。契约文档的存在让确定性从"开发者的自觉"变成"组织的承诺"，这也是本章所有机制的最终归宿。

## 16.16 延伸讨论：数据顺序与调度协同——可复现的另一半

本章聚焦通信层的确定性，但端到端可复现还有"另一半"：数据顺序与调度协同，本节划清两半的接口。数据顺序指每个 rank 每步消费的数据批次序列——它由数据加载器决定，是路由决策的输入（第 16.1 节第一层）；加载器的随机源必须纳入种子链（第 16.9 节），且多 rank 的分片顺序要随全局种子派生（`envs.py` 的全局/本地种子体系，第 2 章），否则"同一全局种子、不同 rank 数据不同"的可复现性断裂。调度协同指多流（计算流与通信流）事件时序的确定语义——DeepEP 的设计在这里有一个隐藏的便利：**数值不依赖调度时序**（第 16.4 节，epilogue 的数学在等待点执行），因此"两半"的协同要求可以简化为：数据顺序确定 + 通信数值确定 = 端到端数值确定，不需要对调度施加确定性（那是做不到的，也是不必要的）。集成方落地时的检查点有三个：加载器的种子接入（框架职责）、DeepEP 配方的启用层级（本章各节）、以及两者交界处的 `topk_idx` 一致性（路由输入确定才能保证槽位与归约的确定，第 16.5 节第六项的句柄只读纪律在此的延伸含义是"路由输入在重放时逐位相同"）。把"另一半"讲清之后，本章的定位就完整了：通信层的确定性机制是必要条件，端到端可复现是必要条件与框架侧充分条件的合取——两个专题（16 与 18）在集成层的分工边界也由此确定。
