# 第 12 章 · 构建与测试体系、昇腾适配与总结展望

## 12.1 构建体系：setup.py 的四个定制行为

`setup.py` 是 DeepEP 构建的中枢，它基于 PyTorch 的 `CUDAExtension`/`BuildExtension`，但在标准流程上做了四处定制（文件头注释自述："把 C++/CUDA 扩展 deep_ep._C 编译进 deep_ep 包，并定制 wheel 打包行为"）：

1. **烘焙集群环境默认值**。`persistent_env_names = ('EP_JIT_CACHE_DIR', 'EP_JIT_PRINT_COMPILER_COMMAND', 'EP_JIT_CPP_STANDARD', 'EP_NUM_TOPK_IDX_BITS', 'EP_NCCL_ROOT_DIR', 'EP_DEFAULT_RDMA_SL', 'EP_OVERRIDE_RDMA_SL')`——构建 wheel 时把这些变量的当前值写进 `deep_ep/envs.py` 的 `persistent_envs` 字典；运行时 `deep_ep/__init__.py` 把它们写入进程环境，**但用户显式设置过的变量优先**（"仅当用户未显式设置该变量时才写入"）。这套"打包时固化集群共性、导入时尊重节点个性"的两级默认，是集群规模部署的关键细节：运维在打包机上设一次 SL/缓存目录，全集群 wheel 生效，单机又能覆盖。
2. **csrc 源码进 wheel**。构建时把 `csrc/` 拷入安装包（注释："把 csrc/ 源码一并拷入 wheel（供 Agent 侧报错时对照源码）"）——设备端模板的 include 路径与运行期排障都依赖源码在场。
3. **版本溯源**。经 `subprocess` 调 git 获取提交哈希、检查工作区状态，写入版本元数据——JIT 缓存键与故障诊断能对应到确切代码版本。
4. **无损导入的元信息加载**。`setup.py` 用 `importlib` 在不触发 `deep_ep.__init__` 的前提下加载 `find_pkgs`——构建过程本身不产生对 PyTorch 运行环境的副作用。

三个脚本的分工：`build.sh`（清理 `build/dist/*.egg-info` → `python setup.py bdist_wheel`，产出不安装的 wheel）、`install.sh`（初始化 DeepJIT 子模块 → 构建 wheel → 安装进当前环境）、`develop.sh`（把扩展链接进源码树，配合测试开发）。README 的安装前置命令 `git submodule update --init --recursive` 拉取的正是 `third-party/deep_jit` 子模块——设备端 JIT 编译框架以源码子模块而非 pip 包的形式供应。

## 12.2 NCCL 依赖：发现、绑定与一致性

DeepEP 与 NCCL 的关系是全仓库最紧的依赖（V2 移除 NVSHMEM 后，RDMA 能力全部来自 NCCL Gin）。三层保障：

**（1）构建/导入期的根目录发现。** `EP_NCCL_ROOT_DIR`（指向含 `include/` 与 `lib/` 的目录）优先于 `NCCL_DIR`，再退到 NVIDIA pip 包的自动发现（`deep_ep/utils/find_pkgs.py` 的 `find_nccl_root`）。版本要求 NCCL ≥ 2.32.3（设备端 API `nccl_device.h` 的窗口/GIN 接口在此之后才稳定）；pip 安装命令直接给出：`python -m pip install "nvidia-nccl-cu13>=2.32.3" --no-deps`。

**（2）运行期唯一性检查。** `deep_ep/__init__.py` 的 `check_nccl_so()` 读取 `/proc/self/maps`，断言进程内**只加载了一份 `libnccl`**（"PyTorch may load another NCCL library, which is different to the linked one"），并把运行库与链接库逐字节比对（`filecmp`）。原因在第 3 章已埋下：设备端通信域（`ncclDevComm_t`）与窗口句柄跨库无效——PyTorch 加载 A 版本、DeepEP 链接 B 版本时，二者共享的通信域就是悬空指针。`EP_SUPPRESS_NCCL_CHECK=1` 可跳过（"不会绕过 C++ 设备通信域的兼容性检查"），且 NCCL < 2.31 时还额外要求编译期/运行期版本完全一致。

**（3）通信域复用。** `EP_REUSE_NCCL_COMM=1`（默认）时，`get_nccl_comm_handle(group)`（`deep_ep/comm/handle.py`）优先复用 PyTorch 进程组后端暴露的 `_comm_ptr`——DeepEP 与 PyTorch 用同一个 NCCL 通信域，不重复建立；否则创建 DeepEP 管理的通信域（`NCCLCommHandle` 的 `managed` 标记，`__del__` 兜底销毁，`destroy_all_managed_nccl_comm()` 供退出前统一清理）。`csrc/kernels/comm/context.cpp` 侧的 `get_local_unique_id()` / `create_nccl_comm(root_unique_id, num_ranks, rank_idx)` / `destroy_nccl_comm()`（内部 `ncclCommAbort`）构成 bootstrap 三件套。

**（4）构建期位宽选择。** `EP_NUM_TOPK_IDX_BITS`（默认 64，可选 32）决定 `topk_idx_t` 的位宽，"更改此值需要重新构建扩展"，运行时以 `deep_ep.topk_idx_t` 类型暴露给用户——路由表的位宽是编译进宿主扩展与设备模板的公共常量（`common/compiled.cuh`），不是运行时开关。

## 12.3 测试体系：从参考实现到基准

`tests/` 目录按子系统划分：`tests/ep/`（`test_ep.py`、`test_prefetch_weights.py`、`test_reduce_grads.py`）、`tests/bucket/`（`test_all_gather.py`、`test_all_reduce.py`、`test_reduce_scatter.py`、`test_mixed.py`、`test_perf.py`、`test_session.py`）、`tests/engram/test_engram.py`、`tests/pp/test_pp.py`、`tests/comm/test_barrier.py`、`tests/buffer/test_allocation.py`、`tests/utils/test_gate.py`。

支撑设施四件套（均在 `deep_ep/utils/`）：

**（1）分布式启动约定。** `deep_ep/utils/envs.py` 的 `init_dist` 约定 `MASTER_ADDR`/`MASTER_PORT`/`WORLD_SIZE`/`RANK`：多节点测试"在每个节点上以共享的 MASTER_ADDR 和 MASTER_PORT 启动同一脚本，将 WORLD_SIZE 设置为节点数、RANK 设置为节点索引"（README）。测试默认 `NCCL_IB_SL=1` 与 `EP_OVERRIDE_RDMA_SL=1`——把测试流量隔离到专用虚拟通道，避免与集群其他负载互相干扰（第 6 章网络配置的测试侧应用）。PP 与 LB 测试还有额外拓扑要求：权重预取/梯度归约测试使用单个 NVLink 域，PP 测试需要仅含 RDMA 的通信组。

**（2）受控负载生成。** `deep_ep/utils/gate.py` 的 `generate_rank_count(num_tokens, num_experts, num_ranks, num_topk, ratio)` 与 `generate_topk_idx(rank_count, …)`：先按比例参数生成"每 token 在各 rank 上的专家计数"（断言每 token 计数和恰为 `num_topk`），再在 rank 组内随机打乱专家顺序得到 `topk_idx`。这让测试能**参数化地复现倾斜/均衡负载**——测试 EP 的最坏情形（单 rank 热点）与最好情形（完美均衡）只需改一个 ratio。

**（3）参考实现与数值校验。** `deep_ep/utils/refs.py` 提供纯 PyTorch 的 dispatch 参考（"Not expanded. Sorted by rank and then by token within each rank"，越界 `recv_topk_idx` 置 -1）；`deep_ep/utils/math.py` 的 `calc_diff(x, y)` 计算 `1 -` Dice 型相似度（转 double、整体 +1 避免除零）作为容差判定。内核输出与参考实现逐位/容差比对，是"内核语义 = 参考语义"的直接证据链（第 4 章的排序语义、第 5 章的归约语义都以此为验收）。

**（4）基准工具。** `deep_ep/utils/testing.py` 提供 `bench`（CUDA 事件计时，30 次预热 + 30 次测量）、`flush_l2_cache`（写 256 MB 零张量冲刷 L2，注释与常量 `l2_flush_cache_size = 256e6`）、以及 `bench_kineto`——解析 PyTorch profiler 的 Chrome trace 提取内核耗时（受 `EP_USE_NVIDIA_TOOLS` 与 `EP_DISABLE_BARRIER_PROFILING` 两个剖析开关控制，README 明确它们"影响 `bench_kineto`，而不影响生产环境通信"）。`tests/bucket/test_perf.py` 是带宽报告的样板。

## 12.4 昇腾适配：同一 API 的另一种硬件

README 新闻区第一条即昇腾发布：**"在华为昇腾 950 NPU 上提供相同的 API 与完整性能"**，细节见独立的 DeepEP-Ascend 仓库。从本文档的分层视角看，这次移植的可行性正是架构设计的回报：

- **Python 缓冲区层与语义完全复用**：`EPBuffer/EngramBuffer/PPBuffer/BucketBuffer` 的生命周期、句柄与事件语义不绑定 NVIDIA 特性；
- **通信后端可替换**：DeepEP 的设备端通信走 NCCL 设备 API 抽象（Gin 在 NVIDIA 上、对应实现在昇腾上），宿主 C++ 层只需替换绑定与内核启动；
- **JIT 编译天然适配异构**：设备端代码本来就是运行期编译的，昇腾侧把 nvcc 后端换成其编译链即可，安装期的"无 GPU 也可装"性质同样成立。

对照社区分支 `uccl/uccl-ep`（"支持 DeepEP 运行在异构 GPU（如 Nvidia、AMD）和网卡（如 EFA、Broadcom、CX7）上"）与 `mori-ep`/ROCm `mori` 后端，可以看到同一模式的多个实例——**分层与抽象不是学术洁癖，而是多硬件生态的入场券**。

## 12.6 全书总结：五条设计原则

把十二章的论证收拢，DeepEP 的架构可以还原为五条原则，每条都有源码层面的落点：

1. **让 GPU 自己通信**（第 6、8、10 章）。计数、同步、发起 RDMA 都在设备端完成：NCCL Gin 设备 API + `NCCLGin` 封装 + notify warp 原子计数 + 设备端两相位屏障，CPU 只在用户要求精确尺寸时（`do_cpu_sync=True`）介入。这是"低延迟 + 重叠"的先决条件。
2. **对称内存作为一等公民**（第 3、4 章）。VMM 分配、fd 跨进程共享、NCCL window 注册、`get_sym_ptr` 直达寻址；`BufferAllocator` 的"先规划后落实"把对称性的全组一致从"约定"变成"类型系统与断言强制"。直达寻址免协商，是一切低开销协议的地基。
3. **解析式配置，免自动调优**（第 1、6、9 章）。SM 数（$\max$ 型带宽模型）、QP 数（65/129/17）、缓冲区大小（`calculate_ep_buffer_size`）、chunk 划分（按 nvl/rdma 带宽比例）全部由拓扑与带宽解析计算，且每次调用可覆盖。EPv2 发布说明将其列为特性："不再需要自动调优"。
4. **布局单一事实来源 + 编译期特化**（第 4、5、11 章）。`layout/` 头文件让宿主与设备共享字节级布局定义；行为开关进模板实参、由 DeepJIT 运行时编译，配合 `EP_JIT_CHECK_NO_SPILLS` 等质量门与多根缓存，兼顾表达力、性能与部署。
5. **机制在库、策略在用户**（第 4、7 章）。路由（gate）、复制规划（`redundancy_mapping`）、等待时机（`EventOverlap`）都开放给调用方；DeepEP 提供 dispatch/combine、权重预取/梯度归约、取数、点对点、桶式集合通信这五类"通信机制"，与 MoonEP/UltraEP 等上层方案解耦。

## 12.7 展望

从主线与分支的走向，可以读出四个正在发生或将要发生的方向：

- **scale-up 域继续扩大**。NVLink 域从 8 卡向更大的机柜级域扩张，"节点内"与"节点间"的边界上移——hybrid 两级路由的划分粒度、QP 规模、`kNumMaxRanks` 类常量都会随之演化（nvDev 分支的 CFT 与 Hybrid-EP 的"更大 NVLink 域"已在探索）。
- **更低比特通信**。FP8 dispatch 已在主线（`use_fp8_dispatch`），NVFP4 出现在 Hybrid-EP 分支；`EP_NUM_TOPK_IDX_BITS` 的构建期位宽选择预示更多数值参数将进入构建期。第 5 章的"通信精度 vs 归约精度"分析框架会持续扩展。
- **零拷贝与 SM 释放**。Zero-copy 与 Normal-SMFree 两条线指向同一终局：让通信占用更少的 SM 与更少的中间拷贝，把 HBM 带宽留给模型本身。
- **异构与生态化**。昇腾 950、ROCm/mori、uccl 的异构网卡支持、DeepXTrace 的慢 rank 诊断——通信库正在从"单硬件专用"走向"多硬件共享协议层"。

MoE 的通信问题会随模型规模持续放大，但问题空间是稳定的：**在带宽、延迟、SM 三面墙下，让每一份数据以最少的同步、最短的路径、最合理的精度抵达目的地**。DeepEP 用本章总结的五条原则给出了一个经过生产检验的答案；理解了这些原则，读者不仅能读懂 DeepEP，也能评估任何下一代 EP 通信系统的设计。

## 12.8 延伸讨论：把测试体系当作语义规范来读

对于集成方与内核开发者，`tests/` 目录的价值不仅在于"验证 DeepEP 是否正常"，更在于它是**可执行的语义规范**：参考实现 `refs.py` 定义了 dispatch 的规范语义（排序规则、越界处理、返回张量的形状约定），测试脚本用 `calc_diff` 把内核输出与规范逐项对齐。换句话说，当文档与直觉发生冲突时，测试是最终的仲裁者。本节按"语义维度"把测试资产重新索引一遍，作为全文的收官索引。

**路由语义**（第 4 章）由 `tests/ep/test_ep.py` 与 `tests/utils/test_gate.py` 共同承载：`generate_rank_count`/`generate_topk_idx` 生成的受控负载使"均衡、倾斜、极端倾斜"三类路由形态都可以参数化复现，而 `refs.py` 的排序语义（先按来源 rank、再按 `src_token_global_idx`）是展开式与非展开式两种布局共同的判定基准。

**数值语义**（第 15 章专题）由 `calc_diff`（`1 -` Dice 型相似度）与各测试的容差选择承载：BF16 归约、FP8 量化、`comm_precision="bf16"` 各有不同的合理容差，测试里的容差值本身就是"该路径精度预期"的量化陈述。

**集合语义**（第 9 章）由 `tests/bucket/` 的六个脚本承载：`test_session.py` 验证会话的替换/恢复纪律，`test_mixed.py` 验证混合域，`test_perf.py` 则是带宽报告模板（`bench_kineto` 解析 Chrome trace，`flush_l2_cache` 用 256 MB 写零冲刷 L2 保证测量干净）。

**生命周期语义**（第 3 章）由 `tests/buffer/test_allocation.py` 承载：分配计划的规划与落实、跨组注册、计划一致性断言，都是 `BufferAllocator` 契约的可执行版本。

**专项原语语义**（第 7、8 章）由 `tests/ep/test_prefetch_weights.py`、`tests/ep/test_reduce_grads.py`、`tests/engram/test_engram.py` 承载——它们同时示范了 README 强调的三条纪律：LB 映射的域内一致与自复制禁忌、梯度归约前的初始化与归约后的不清零、Engram 逐层钩子的等待顺序。

最后是**运行拓扑语义**：多节点测试的启动约定（共享 `MASTER_ADDR`/`MASTER_PORT`、`WORLD_SIZE` 为节点数、`RANK` 为节点索引）、测试默认的 `NCCL_IB_SL=1` 与 `EP_OVERRIDE_RDMA_SL=1`、LB 测试的单 NVLink 域要求与 PP 测试的纯 RDMA 组要求——这些约定把"拓扑即输入"的 DeepEP 世界观延伸到了测试环境本身。

## 12.9 延伸讨论：wheel 的内容与可复现安装

第 12.1 节概述了 setup.py 的定制行为，本节从"一个 wheel 里到底有什么"的角度把它拼成完整的部署图景，并讨论可复现性。一个 DeepEP wheel 包含四类内容：其一，编译产物 `deep_ep._C` 宿主扩展（pybind11 绑定、缓冲区运行时、内核启动封装、对称内存分配器、JIT 入口）；其二，Python 包（`deep_ep/` 的缓冲区、通信、工具模块）；其三，**csrc 源码拷贝**（第 12.1 节第 2 条定制，供设备端 JIT 编译作为源料、并供排障时对照）；其四，`deep_ep/envs.py` 的 `persistent_envs`（第 12.1 节第 1 条烘焙，集群默认值）。加上 `deep_ep/__init__.py` 的 `check_nccl_so` 与版本溯源信息（git 哈希，第 12.1 节第 3 条），这四类内容共同保证了"安装包即自足环境"：不需要仓库、不需要额外源码树，运行环境里就有 JIT 所需的全部模板头（第 11 章的 `init_jit` 以包内路径为源料根）。

可复现性视角下有两个值得注意的点。第一，烘焙的环境默认值意味着**同一个 wheel 在不同集群是"同一份代码 + 不同的默认环境"**——若运维需要区分，可以在导入后用环境变量覆盖（用户值优先，第 12.1 节），或在打包时为不同集群构建不同 wheel。第二，`EP_NUM_TOPK_IDX_BITS` 这类"构建期常量"被烘焙后，wheel 与宿主扩展的位宽绑定（第 12.2 节），运行时覆盖无效——因此为不同位宽需求部署时，必须构建不同的 wheel 并在版本元数据中区分，这也是 git 哈希被写入版本信息的工程动机之一（可复现安装的最低要求是"能回答这个二进制从哪来"）。

## 12.10 延伸讨论：多节点测试的组织与常见坑

第 12.3 节给出了多节点测试的启动约定，本节补充组织层面的实践，因为多节点测试的失败大多数不是代码问题而是组织问题。第一是**启动编排**：约定要求每个节点以相同的 `MASTER_ADDR`/`MASTER_PORT` 启动同一脚本、`WORLD_SIZE` 为节点数、`RANK` 为节点索引（`init_dist` 约定，第 12 章）——手工在每个节点上开终端的方式极易出错（漏启动一个节点会让所有 rank 卡在构造屏障，第 14 章问题三），实践上应使用任务编排系统或脚本循环拉起，并保证各节点启动的时间窗在超时容忍之内。第二是**网络前置检查**：测试默认的 `NCCL_IB_SL=1` 与 `EP_OVERRIDE_RDMA_SL=1` 要求交换机侧已配置对应的 SL 到 VL 映射（第 6 章）；带宽探测（`nvidia-smi` 与 `ibstat`）必须在每个节点可用——BucketBuffer 会直接拒绝构造（第 6.5 节）。第三是**拓扑前提的核对**：权重预取与梯度归约测试要求单个 NVLink 域、PP 测试要求仅含 RDMA 的通信组（第 12 章）——用 `get_physical_domain_size` 与 `get_logical_domain_size` 的返回值在测试开头打印并核对，能提前暴露大半的"环境不对"问题。第四是**剖析干扰的隔离**：`EP_USE_NVIDIA_TOOLS` 与 `EP_DISABLE_BARRIER_PROFILING` 只影响 `bench_kineto` 的测量路径（第 12 章），做性能对比时要固定它们的取值。这四条组织纪律与第 14 章的故障诊断链互为表里：先核对组织项，再进入代码级排查。

## 12.11 延伸讨论：离线与受限环境的安装清单

生产集群常处于网络受限环境（不能随意访问外网），本节给出"离线安装"的完整清单，全部步骤对应仓库内已论证的机制。第一步，准备离线依赖包：PyTorch 2.10 及以上（CUDA 版）、`nvidia-nccl-cu13>=2.32.3`（或 CUDA 12 对应包，`--no-deps` 安装，第 12.2 节）、以及 CUDA Toolkit 13.1 及以上与支持 `std::format` 的 C++20 工具链（第 11.4 节 nvcc 发现链的前置）。第二步，源码与子模块：`git submodule update --init --recursive` 拉取 `third-party/deep_jit`（第 11.2 节），确认 `third-party/tilelang_ops` 一并就位；离线环境建议以镜像仓库或源码包形式供应整棵树。第三步，构建 wheel：`bash install.sh`（或先 `build.sh` 再安装，第 12.1 节），构建机需要 NCCL 头文件与库（`EP_NCCL_ROOT_DIR` 指向离线部署的 NCCL 目录，优先级高于 `NCCL_DIR` 与 pip 发现，第 12.2 节）；构建机上无需 GPU（第 2.6 节安装期不编设备代码），这使离线构建可以在独立的编译节点完成。第四步，烘焙集群默认值：构建前设置 `persistent_env_names` 清单中的变量（`EP_JIT_CACHE_DIR`、SL 相关、位宽，第 12.1 节），让 wheel 自带集群约定。第五步，目标节点校验：导入 `deep_ep` 触发 `check_nccl_so`（第 12.2 节，确认运行库与链接库一致）、核对 JIT 工具链发现（nvcc 四级发现链，第 11.4 节）、按第 12.10 节清单做首次构造验收。清单的关键洞察是：离线安装的难点不在 DeepEP 本身（安装期零 GPU 依赖），而在 NCCL 与工具链的一致性——第 12.2 节的三层保障（发现、唯一性、复用）正是为这类环境设计的，逐条核对即可完成部署。
