# 第 07 章 · 专家负载均衡与权重预取（EPLB 原语）

## 7.1 问题：热点专家与"算力借调"

MoE 的 top-k 门控天然产生负载倾斜：少数"热门专家"可能在某个微批次里被数倍于平均值的 token 命中，其所在 rank 的专家 GEMM 时长成为整层的木桶短板。**专家负载均衡（Expert-Parallel Load Balancing，EPLB）**有两类应对：

- **静态重排**：在训练步之间根据历史负载重新分配专家到 rank。有效但滞后，且跨 rank 迁移专家权重的代价大。
- **动态冗余复制（dynamic expert replication）**：在微批次内，把热点专家**复制**一份到 NVLink 域内另一个 rank 的"冗余槽位"，让两个 rank 分摊该专家的计算。复制发生在前向计算之前、且只复制权重（不动缓存），代价小、反应快。

DeepEP V2.5 为第二类方案提供了两个通信原语（README V2.5 发布说明：*"新增 `EPBuffer.lb_prefetch_weights` 和 `EPBuffer.lb_reduce_grads` 以支持动态冗余专家：在专家计算之前通过 NVLink 预取专家权重与量化 scale，然后在反向传播时将冗余专家的 FP32 梯度累加回原始专家"*），并明确说明这些原语支持 MoonEP 与 UltraEP 探索的专家复制方案。注意 DeepEP 的边界：**它只提供"复制权重"与"归还梯度"两个交换操作，复制规划（谁复制谁）与 token 重路由由调用方负责**（README："调用方负责提供复制规划、将 token 重路由到所选的专家实例，并管理专家 GEMM"）。

## 7.2 复制模型与 redundancy_mapping 语义

设 NVLink 域内有 $P_{\text{nvl}}$ 个本地 rank，每 rank 持有 $N_{\text{local}}$ 个本地专家（$\text{num\_local\_experts}$），另有 $R$ 个冗余槽位（$\text{num\_redundant\_experts}$）。专家编号采用全局坐标：

$$
\text{expert\_id} = \text{owner\_rank} \times N_{\text{local}} + \text{local\_expert\_idx},
$$

即"属主 rank × 每 rank 专家数 + 属主内偏移"。复制计划由调用方给出为一张映射表 `redundancy_mapping`，其规范（README + `deep_ep/buffers/ep.py` 的 docstring）值得逐条列出，因为它同时是正确性与性能的契约：

| 约束 | 内容 | 为什么 |
| --- | --- | --- |
| 形状 | `[num_nvlink_ranks, num_redundant_experts]`，int32、CUDA、连续 | 行 = 冗余槽位所在的本地 rank，列 = 冗余槽位编号 |
| 取值 | `[r, c] = expert_id` 表示"域内本地 rank $r$ 的第 $c$ 个冗余槽位复制该专家"；未用槽位为 `-1` | 内核按表逐槽位生成任务 |
| 一致性 | 域内**每个 rank 持有完全相同的表** | 集合通信需要全组共享计划 |
| 禁忌 | **某个 rank 自己的专家不得出现在它自己的冗余槽位**（副本必须给其他 peer） | 自复制无带宽意义，且与"归约时读对端"的假设冲突 |
| 存续 | 在对应交换完成之前保持映射与张量存储有效 | 内核按引用读取 |

前向与反向必须使用**同一张映射表**（README："请使用与前向传播相同的映射"）——权重复制到哪里，梯度就要从哪里收回来，这是一对镜像操作。

## 7.3 lb_prefetch_weights：把权重推到冗余槽位

### 7.3.1 接口语义

```python
weights_ready = buffer.lb_prefetch_weights(
    redundant_expert_weights,   # 冗余槽位张量（位于 LB 区域，形状 [num_redundant_experts, …]）
    expert_weights,             # 原始专家权重（普通 CUDA 分配，形状 [num_local_experts, …]）
    redundancy_mapping,
)
# … 独立计算可与之重叠 …
weights_ready.wait()
# 此后冗余副本的权重就绪，可执行专家计算
```

接受"单个张量或相互匹配的非空张量序列"（README：*"它接受单个张量或相互匹配的非空张量序列，因此权重与量化 scale 可以一起传输而无需 dtype 转换"*）——量化专家的权重与 scale factor 常是不同 dtype 的两个张量，序列形式让它们在同一次交换里走完，避免拆成两次调用与两次 dtype 摊平。最高维语义：原始权重最高维为 `num_local_experts`、冗余张量为 `num_redundant_experts`，尾部形状可以不同，**只要每个匹配对"每专家字节数"相同**，且是 `deep_ep.get_num_tma_alignment()`（32 字节）的倍数——TMA 搬运的基本约束。

### 7.3.2 内核实现：warp 私有 chunk 的流水

宿主侧入口 `csrc/kernels/ep/prefetch_weights.hpp` 的 `launch_lb_prefetch_weights(context, num_weights, layout::EPWeightList weights, redundancy_mapping, num_redundant_experts, num_local_experts, num_sms, stream)`，实现要点：

```cpp
// 每个 warp 私有一个定长 chunk 缓冲，自己负责加载与存储
constexpr int num_chunk_bytes = 12 * 1024;   // 每个 chunk 12 KiB
```

即"**warp 私有 12 KiB chunk、加载与存储一体**"的流水模型：每个 warp 从任务表取出一条复制任务（原专家 → 冗余槽位），按 12 KiB 的 chunk 循环——把 chunk 从属主 rank 的权重经 NVLink 读入私有缓冲，再写入本 rank 的冗余槽位区域。任务表的编译期支撑在 `deep_ep/include/deep_ep/layout/ep/eplb.cuh`：

```cpp
// 一条 EPLB 任务：把一个"原专家"的权重交换到某个"冗余专家槽位"
struct EPLBTask {
    int local_expert_idx;      // 本 rank 上要复制的原专家在其本地位中的编号
    int dst_nvl_rank_idx;      // 冗余专家槽位所在的 NVL rank 编号
    …
};
```

任务的生成涉及把映射表压缩成每 rank 的任务列表，`eplb.cuh` 引入了 CUB 的块级前缀和（`cub/block/block_scan.cuh`，注释：*"BlockScan，用于任务压缩"*）——多 warp 并行扫描映射表时，"非空槽位"经 block scan 得到在任务数组中的写入位置，避免原子冲突或两遍扫描。

**为什么叫 prefetch（预取）？** 通信时序上，这次交换发生在**专家计算之前**：调用方在 gate/规划完成后立即发起，`weights_ready.wait()` 之前的窗口正好用于其他计算（README 的示例在两行注释里写明 *"independent computation can overlap the exchange"*）。专家权重动辄数百 MiB，这次 NVLink 搬运若串行执行会直接拉长每层时延；预取把它藏进"规划→计算"的间隙，效果等同于把权重加载延迟隐藏掉（README：*"隐藏权重加载延迟"*）。它也与第 4 章 dispatch 的 epilogue 机制形成互补：dispatch 藏的是 token 搬运，prefetch 藏的是权重搬运。

### 7.3.3 LB 区域：独立于 dispatch/combine 的存储

冗余槽位的张量必须位于 EPBuffer 的 **LB 区域**——构造时经 `lb_allocation_plan_or_num_bytes` 传入（`BufferAllocator` 计划或对齐字节数），落实在 `runtime.lb_storage` 上（见第 3 章构造时序第 3/7 步）。README 的设计理由：

- "该 LB 区域与 EP 的 dispatch/combine 缓冲区相互独立"——权重交换的流量形态（大块连续、NVLink only）与 token 通信（小槽位、两级路由）完全不同，合并到一个缓冲区会互相干扰布局规划；
- "冗余张量必须位于其中；原始专家权重与梯度可以使用普通的 CUDA 分配"——冗余槽位是对称内存（对端要能直达写入），原始权重只在属主本地读，不需要对称性；
- "在 NVLink 域内的每个 rank 上，规划必须具有相同的形状和分配顺序"——对称性的全组一致要求（第 3 章 3.6 的推论）。

## 7.4 lb_reduce_grads：把梯度还回属主

### 7.4.1 接口语义

```python
# After backward has written redundant_grads and the local expert_grads:
grads_ready = buffer.lb_reduce_grads(
    redundant_grads,    # 冗余槽位的 FP32 梯度（[num_redundant_experts, D]，位于 LB 区域）
    expert_grads,       # 属主专家的 FP32 梯度（[num_local_experts, D]），需先初始化
    redundancy_mapping, # 与前向相同的映射
)
grads_ready.wait()
# expert_grads 现在包含所有冗余副本的贡献
```

约束：二维 FP32、"请将每个专家的参数展平为一行，并保持相同的字节对齐"（README）；调用前"用本地贡献（或零）初始化 `expert_grads`"；归约**不清零**冗余梯度——"在下一次累加之前请覆盖它们或将它们置零"。这三条合起来构成清晰的累加语义：

$$
\text{expert\_grads}[e] \;\mathrel{+}=\; \sum_{c:\ \text{map}[r,c]=e}\ \text{redundant\_grads}[c] \quad (\text{属主 rank } r \text{ 上}),
$$

属主自己的贡献已在本地梯度里，因此必须**先**初始化再累加。

### 7.4.2 内核实现：24 KiB chunk

`csrc/kernels/ep/reduce_grads.hpp` 的 `launch_lb_reduce_grads(context, redundant_expert_grads, expert_grads, redundancy_mapping, num_redundant_experts, num_local_experts, hidden, num_sms, stream)`，其注释同样直白：

```cpp
// Each warp owns one chunk buffer  // 每个 warp 私有一个定长 chunk 缓冲
constexpr int num_chunk_bytes = 24 * 1024;   // 每个 chunk 24 KiB
```

与权重预取的 12 KiB 对比，chunk 翻倍的原因是**访问模式的对称性差异**：预取是"读属主 + 写本地"，两个方向都是对本地显存的常规访问，chunk 只受私有缓冲占用约束；梯度归约是"读**对端** + 写本地 + 累加"，读远端 FP32 的有效带宽更低、且要等待对端数据就绪，更大的 chunk 摊薄每次往返的固定开销、提升单 warp 的聚合读带宽。两个内核共用同一"任务表 + warp 私有 chunk"骨架，差别只在 chunk 尺寸与是否有累加语义——这是"同构问题、同构解法"的又一例证。

### 7.4.3 FP32 梯度的精度考虑

为什么梯度归约强制 FP32？优化器状态与梯度累加通常在 FP32（混合精度训练的 master weight/grad）；若先降精度再归约，误差会进入参数更新路径且不可逆。这与 combine 的选择（BF16 激活归约）形成对照——**激活的舍入误差被下一层量化/非线性吸收，参数梯度直接进优化器，精度要求更硬**。代价是通信量为 BF16 的两倍，但梯度归约的量只有冗余专家数 × hidden，远小于 token 通信，可以承受。

## 7.5 集合性与生命周期纪律

这两个原语有一条容易被违反的纪律（README："它们在通信流上异步执行并返回一个 `EventOverlap`"之上的前提）：**集合性**——"这两个交换操作在每个 NVLink 域内都是集合性的：该域中的每个 rank 都必须调用它们，包括未被分配冗余槽位的 rank"。原因是任务分发依赖全组一致的映射表与屏障同步：域内某个 rank 不调用，对端等待其贡献/确认的 warp 将一直空转（由第 10 章的 GPU 超时机制兜底报错，但性能已损）。

生命周期纪律同样来自 README：

- "在对应的交换完成之前，请保持映射与张量存储有效"——内核按引用读映射表与权重；
- "如果冗余存储在多个层或微批次间被复用，请在反向计算之前恢复所需的权重，并在复用其输入之前完成梯度归约"——LB 区域是复用的暂存区，跨层复用时前向写入的副本会被下一层的预取覆盖，因此必须在该层反向读尽之前不被覆盖；
- `previous_event` 可指定输入就绪时机，`num_sms=0` 走解析式估算（`lb_get_theoretical_num_sms`）。

## 7.6 端到端时序与 MoonEP/UltraEP 的映射

```text
  gate/规划器(CPU/GPU)  →  redundancy_mapping（域内一致）
        │
        ├──lb_prefetch_weights（comm 流，NVLink 集合交换）──▶ weights_ready
        │        └─ 间隙：可重叠的独立计算
        ▼
  专家计算（副本 rank 也算热点专家；token 已被调用方重路由）
        │
        ▼
  反向：专家参数梯度 → redundant_grads（副本 rank）+ expert_grads 初始化（属主）
        │
        ├──lb_reduce_grads（comm 流，NVLink 集合归约）──▶ grads_ready
        ▼
  优化器更新（属主 expert_grads 已含全部副本贡献）
```

MoonEP（在线规划、权重预取与梯度归约）与 UltraEP（按 post-gating 负载规划复制与 token 重路由、把复制保持在 NVLink 域内）分别对应这张时序图的不同填法——DeepEP 提供的是图中两根"交换管道"，规划策略完全开放。这也是 DeepEP API 的一贯姿态：**机制在库里，策略在用户**（对照：dispatch 的路由策略也在用户的 gate 里）。

## 7.7 本章小结

- 动态冗余复制把热点专家的权重复制到 NVLink 域内其他 rank、反向把 FP32 梯度归约回属主；DeepEP 提供 `lb_prefetch_weights`/`lb_reduce_grads` 两个集合原语，规划与重路由留给调用方（MoonEP/UltraEP 的集成点）。
- `redundancy_mapping` 是 `[num_nvlink_ranks, num_redundant_experts]` 的 int32 CUDA 表，条目为全局专家编号（`owner_rank*num_local_experts+local_expert_idx`）或 `-1`，全组一致、前向反向同表、禁止自复制。
- 权重预取内核：每 warp 私有 12 KiB chunk、EPLBTask 任务表（`eplb.cuh`）+ CUB BlockScan 压缩；支持张量序列（权重+scale 同传）、32 字节 TMA 对齐、独立 LB 区域（`lb_allocation_plan_or_num_bytes`）。
- 梯度归约内核：每 warp 24 KiB chunk（读对端带宽更低、chunk 更大摊薄往返）、FP32、累加语义（先初始化、不清零）。
- 两条纪律：NVLink 域内集合性（所有 rank 必须调用）、交换完成前映射与存储必须有效、跨层复用 LB 区域时先恢复权重/先完成归约。

## 7.9 延伸讨论：任务表的并行生成与 BlockScan 的作用

第 7.3.2 节提到 `eplb.cuh` 用 CUB 的块级前缀和做"任务压缩"，本节把这个机制论证完整——它是设备端把一张静态映射表转化为并行任务列表的标准范式。问题定义：`redundancy_mapping` 是一张 `[num_nvlink_ranks, num_redundant_experts]` 的表，其中非 `-1` 的条目是复制任务；内核需要把这张稀疏的表变成每 rank 的紧凑任务数组，供 warp 按 `EPLBTask`（`local_expert_idx`、`dst_nvl_rank_idx` 等，第 7 章）逐条消费。朴素做法有两种，都不理想：串行扫描把所有任务交给单线程生成，成为内核启动的串行头部；原子写入任务数组则需要"先数总数再分配"的两遍逻辑或预分配上限的浪费。

BlockScan 方案的处理方式：让块的每个线程负责一个映射表条目，产出"该条目是否是任务"的标志；对标志做块级前缀和（`cub/block/block_scan.cuh`，第 7.3.2 节注释"BlockScan，用于任务压缩"），每个任务条目在前缀和中的位置就是它在紧凑任务数组中的唯一写入下标——一次并行扫描同时完成计数与定位，既无原子冲突也无两遍扫描。这与 dispatch 的"计数、前缀和、槽位"（第 4 章）是同一范式在任务调度层的重演：**用前缀和把"动态数量"转化为"确定性位置"**。两者的深层一致性也解释了为什么 EPLB 任务可以参与确定性调度（第 16 章）：任务编号是映射表的确定函数，与执行顺序无关。

## 7.10 延伸讨论：chunk 尺寸的设计推导

权重预取每 warp 12 KiB、梯度归约每 warp 24 KiB（第 7 章），这两个数字背后有一条可复用的推导路径，值得作为内核参数设计的范例记录。设每 warp 的私有缓冲占用为定值（内核以 `constexpr` 写死，如 `num_chunk_bytes`），内核要满足每 SM 一个 block 的占用约束（`__launch_bounds__(kNumThreads, 1)`，第 10 章），则 chunk 的上限由 SM 的寄存器与共享内存预算除以并行 warp 数决定；chunk 在这个上限内取值，越大越好——单次拷贝的固定开销（发起、等待、地址计算）被摊薄到更多有效字节上。权重预取读的是属主本地显存（属主 rank 的 `expert_weights` 可以是普通 CUDA 分配，第 7 章），写的是本地 LB 区域，两侧都是低延迟本地访问，较小 chunk 即可流水；梯度归约读的是对端显存（经 NVLink 的对称直达），每次读取都要等待远端数据就绪，往返固定延迟更高，因此 chunk 加倍以摊薄等待——这就是 12 KiB 与 24 KiB 之比的来源逻辑。推广为经验公式：chunk 尺寸应随"单次访问的有效延迟"增长，而有效延迟由访问路径（本地、对端、网络）决定。第 9 章的 bucket chunk（按带宽比例划分）与第 13 章的调优实践会呈现同一思想的其他表现形式。

## 7.11 延伸讨论：与静态重排的组合策略

动态复制（本章主题）与静态重排（训练步之间重新分配专家位置）并不互斥，成熟的部署通常组合两者，而组合的关键在于认清两者的时序与成本差异。静态重排跨微批次生效，其成本是跨 rank 迁移专家权重（大流量、可离线、不占训练关键路径），收益是改变负载分布的底座——把长期热点搬到更空闲的位置。动态复制在微批次内生效，其成本是每层的 NVLink 预取与梯度归约（第 7 章账本），收益是吸收短期波动——静态重排之后残余的热点。组合的策略空间在于：静态重排把分布的长尾压平到动态复制可处理的范围（负载因子 $\lambda$ 的最大值下降，复制份数需求随之下降）；动态复制的规划器（消费 `cumulative_local_expert_recv_stats` 统计，第 4 章）反过来为下一轮静态重排提供数据。DeepEP 在这个组合中的角色边界清晰：静态重排是框架的专家放置决策，动态复制的两根交换管道是 `lb_prefetch_weights` 与 `lb_reduce_grads`；接口上唯一的耦合点是 `redundancy_mapping` 必须与当层的专家放置一致（专家编号 `owner_rank * num_local_experts + local_expert_idx` 的坐标，第 7 章）。静态重排发生时，映射表的坐标系随之更新——集成方应把"放置变更"与"映射表重算"绑定为同一个原子步骤，否则前向反向的坐标错位会造成第 14 章问题八那一类的梯度错误。

## 7.13 延伸讨论：复制决策的数据流闭环

动态复制的完整工程闭环包含五个环节，本节把它们串成数据流，帮助集成方检查自己的规划器是否闭合。环节一，**观测**：`cumulative_local_expert_recv_stats` 的差分给出每步的专家负载分布（第 4 章契约表、第 18.11 节差分提醒），必要时补充门控概率的直方图——观测的分辨率决定规划的上限。环节二，**决策**：规划器按收益模型（第 7.8 节账本）选出要复制的专家与份数，输出 `redundancy_mapping`——决策要遵守两条硬约束（不自复制、域内一致，第 7.2 节）与一条时序约束（决策在预取发起前完成）。环节三，**交换**：`lb_prefetch_weights` 把权重推到冗余槽位（第 7.3 节），期间调用方做独立计算——交换的完成以 `weights_ready.wait()` 为界。环节四，**执行与归还**：专家计算、反向、`lb_reduce_grads` 归还梯度（第 7.4 节），归约的完成以 `grads_ready.wait()` 为界。环节五，**对账**：下一次观测验证决策效果（热点 rank 的负载因子是否如 $\lambda/r$ 预期下降，第 7.8 节收益模型），未达预期的偏差回灌环节二的模型（例如发现复制后瓶颈转移到传输，则按第 1.10 节切换治理层）。五个环节中，DeepEP 承担环节三与四的通信机制，其余三环是规划器的职责（第 20.7 节"机制在库、策略在用户"）——检查自己部署时的自查问题因此清晰：观测的分辨率够吗、决策遵守硬约束了吗、交换与归回的等待点放对了吗、对账周期与漂移速度匹配吗（第 19.14 节冲击五）。闭环里最常见的断点是环节五的缺失——复制了但不验证效果，规划器退化为开环控制，漂移迟早吞噬收益。

## 7.12 延伸讨论：复制方案的带宽账本与退化情形

动态复制的收益不是免费的，本节把账算清楚，帮助集成方判断"什么规模的热点才值得复制"。

**复制一张权重表的成本**。设专家权重为 $W$ 字节，某热点专家要复制 $r$ 份到 $r$ 个不同 rank 的冗余槽位。前向预取的通信量为 $r \cdot W$（从属主推送到 $r$ 个副本），全部走 NVLink；反向归约的通信量同样是 $r \cdot W$ 量级（FP32 梯度，若权重是 BF16 则梯度字节数翻倍）。合计每层每热点专家的均衡负载代价约为 $r \cdot (W + W_{\text{grad}})$ 字节，且这一代价**在 NVLink 域内所有 rank 上是集合性的**——即使某个 rank 没有任何冗余槽位，它也要参与屏障与交换流程。因此复制的决策粒度是"每层、每热点专家、每微批次"，规划器必须在收益（热点 rank 计算时间下降）与代价（NVLink 带宽被占用、所有 rank 的等待）之间权衡。

**收益的上限模型**。设某热点专家的 token 负载是均值的 $\lambda$ 倍，复制 $r$ 份后每份承担约 $\lambda / r$ 倍负载。层时间的短板从 $\lambda$ 缩到 $\max_{\text{其他热点}} (\cdot, \lambda/r)$——只有当 $\lambda/r$ 降到次高热点之下时，继续复制才不再改善短板。把 $\lambda$ 的分布画出来（这正是 `cumulative_local_expert_recv_stats` 与 `tests/utils/test_gate.py` 负载生成器的用武之地），就能算出"每层应该复制几个专家、各复制几份"的解析解。MoonEP 与 UltraEP 的区别本质上就是这个解析解的计算时机与信息集不同：前者在线规划、后者按门控后的负载规划（README 引用）。

**两个退化情形**。其一，全组负载完美均衡（$\lambda \equiv 1$）：此时 `redundancy_mapping` 全为 `-1`，两个原语退化为"纯集合屏障 + 零传输"——开销仅剩同步本身，这正是"未被分配冗余槽位的 rank 也必须调用"这一纪律的代价上限，也说明调用方应当为"本批无热点"设计快速通道（跳过调用或传入空映射）。其二，极端倾斜（$\lambda$ 巨大且只有一两个热点）：复制份数受 NVLink 域内 rank 数限制（每 rank 至多放一个副本，因为"自己的专家不能放进自己的槽位"），若 $\lambda$ 超过域内可分摊的上限，就必须回到静态重排或降低该专家的命中频率（门控端处理）——通信原语解决不了门控分布本身的问题。

**与第 5 章归约的呼应**。冗余梯度归约（`lb_reduce_grads`）与 combine 的多重归约共享一个纪律：参与方集合固定、顺序由映射决定。映射表在域内一致且前向反向同表，使得归约的"贡献图"是静态已知的——这比 combine 的动态路由更容易做确定性（第 16 章将讨论确定性与映射的关系）。FP32 的强制（而非 BF16）则源于梯度直接进优化器的精度要求，这一点与 reduce-scatter 的 `comm_precision="bf16"`（激活/DP 梯度场景，误差可被吸收）形成精度光谱上的两个端点。
