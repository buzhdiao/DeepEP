# DeepEP 原理性介绍 · 总目录

> 本文档是 DeepEP（DeepEveryParallel）仓库的原理性长文，由一个总目录、十二个主章（第 01~12 章）与八个专题章（第 13~20 章）组成，全篇逾十万汉字。它不是 API 手册，而是一套"为什么—是什么—怎么实现"的完整论证：每一章先讲清楚该项设计要解决的问题与物理约束，再讲原理、协议流程、内存布局与设计权衡（用公式、流程图、ASCII 结构图与表格讲透），最后落到具体代码实现（引用真实存在的文件路径与函数名）。全部引用均取自仓库源码与 README，未杜撰任何接口。

## 一、DeepEP 是什么：一段话导读

DeepEP 是一个面向机器学习训练与推理的高性能通信库。它为 MoE 的 dispatch/combine（分发/聚合）提供高吞吐、低延迟的专家并行（expert parallelism，EP）all-to-all GPU 内核，包括 FP8 dispatch，以及面向冗余专家的 NVLink 权重与梯度交换；同时提供面向流水线并行（PP）、上下文并行（CP）、数据并行（DP）与远程内存访问（Engram）的实验性原语。通信内核在运行时通过 DeepJIT 编译，宿主端扩展则在安装期间构建。V2.5 版本将原先统一的 ElasticBuffer 拆分为 `EPBuffer`、`EngramBuffer`、`PPBuffer` 与 `BucketBuffer` 四个缓冲区，它们共享 `BufferBase` 生命周期，并由 `BufferAllocator` 在构建缓冲区之前规划对称张量（symmetric tensor）的布局。底层通信建立在 NCCL 的 Gin（GPU Initiated Networking）设备端后端之上，V1 的 NVSHMEM 后端已被完全移除。

理解 DeepEP 的钥匙只有一把：**一切设计都围绕"让 GPU 自己发起通信，并把通信塞进计算留下的缝隙里"**。围绕这把钥匙，文档反复回到五个母题——对称内存寻址、设备端通信原语（NCCL Gin）、两相位屏障与 mbarrier 同步、事件驱动的计算/通信重叠、以及解析式（而非自动调优）的资源配置。

## 四、术语表

按主题分组，按拼音/字母排序；"→" 表示参见。

**并行与模型侧**

| 术语 | 释义 |
| --- | --- |
| MoE（Mixture of Experts） | 混合专家层：门控 $g$ 为每个 token 选出 top-k 专家，输出为被选专家输出的加权和，参数量与计算量解耦（第 1 章）。 |
| 专家并行（EP） | 将 $E$ 个专家均分到 $P$ 个设备，token 需要跨设备寻找其目标专家（第 1 章）。 |
| dispatch（分发） | 把 token（及其路由元数据）发送到其目标专家所在设备的 all-to-all 操作；反向传播中它同时是 combine 的反传形式（第 4 章）。 |
| combine（聚合） | 把专家输出按路由权重归约回 token 原属设备的 all-to-all 操作；反向传播中它同时是 dispatch 的反传形式（第 5 章）。 |
| top-k 路由 | 每 token 选 $k$ 个专家；索引张量 `topk_idx`（类型 `deep_ep.topk_idx_t`，构建期可选 32/64 位），`-1` 表示未选中（第 4 章）。 |
| 展开布局（expanded layout） | 每 token 每个专家槽一个槽位的输出布局，面向分组专家 GEMM；配 `expert_alignment` 与 `do_zero_padding`（第 4 章）。 |
| epilogue（收尾操作） | 通信内核之后的数据整理步骤（拷贝出 `recv_x`、写 bias 等），可延迟到 `current_stream_wait()` 执行（第 4/5 章）。 |
| EPLB / 冗余专家 | 专家负载均衡：把热点专家复制到 NVLink 域内其他 rank（冗余槽位），前向预取权重、反向归约梯度（第 7 章）。 |
| PP / CP / DP | 流水线并行 / 上下文并行 / 数据并行；DeepEP 用 PPBuffer 与 BucketBuffer 覆盖其通信（第 9 章）。 |
| Engram | 按条目索引的远程参数存储：各 rank 持有分片，`fetch()` 经 RDMA 按索引取数，逐层给出等待钩子（第 8 章）。 |

**网络与传输侧**

| 术语 | 释义 |
| --- | --- |
| scale-up / scale-out | 节点内 NVLink 域（高带宽对称访问）与跨节点 RDMA 域；`get_logical_domain_size()` 返回两者的 rank 数（第 6 章）。 |
| 物理域 | 由 NCCL 实际连通性决定的域：`get_physical_domain_size()` 返回（RDMA rank 数，NVLink rank 数）（第 6 章）。 |
| NVLink / LSA | 节点内高带宽互连；NCCL 设备 API 中对应 LSA 团队（`ncclTeamTagLsa`）（第 6/10 章）。 |
| RDMA / QP | 远程直接内存访问与其队列对（Queue Pair）；DeepEP 预分配 65/129/17 个 QP（第 6 章）。 |
| GIN（GPU Initiated Networking） | NCCL 的设备端通信后端：GPU 代码直接发起 RDMA 读/写/原子/多播，DeepEP 的 RDMA 路径全部构建其上（第 6/8 章）。 |
| window（`ncclWindow_t`） | 对称内存注册窗口；持有窗口即可用 `get_sym_ptr()` 把本地指针换算成对端指针（第 3/10 章）。 |
| hybrid（混合模式） | 跨节点先经 RDMA 到目标节点、再经 NVLink 节点内分发的两级路由；与"直连（direct）"相对（第 6 章）。 |
| multimem | NVLink 的多播/归约地址空间，NVLink 侧 all-reduce 依赖 NCCL 的 multimem 支持（第 9 章）。 |
| SL / VL | RDMA 服务等级与 InfiniBand 虚拟通道，用于专家流量与其他流量的隔离（第 6 章）。 |
| 自适应路由 / PCI 原子模式 | InfiniBand 交换机多路径特性；`PCI_ATOMIC_MODE=4` 提升 RDMA 原子性能（第 6 章）。 |

**GPU 与内核侧**

| 术语 | 释义 |
| --- | --- |
| 对称内存（symmetric memory） | 各 rank 布局一致的共享显存，基于 CUDA VMM 与跨进程 fd 共享构建；`shared_handle_t=(pid, fd)`（第 3 章）。 |
| mbarrier | GPU 硬件异步屏障对象（`cuda::barrier<thread_scope_block>`），支持相位（parity）等待，TMA 完成通知的载体（第 10 章）。 |
| TMA | Tensor Memory Accelerator 批量异步拷贝引擎；相关对齐常量为 32 字节（`deep_ep.get_num_tma_alignment()`）（第 4/10 章）。 |
| 两相位屏障 | `BarrierSignals` 用计数器 + 两个交替的相位标志实现可复用的 NVL 屏障，避免残留值干扰下一相位（第 10 章）。 |
| notify warp | dispatch/combine 内核中专职统计接收计数的 4 个 warp（`kNumNotifyWarps=4`）（第 4 章）。 |
| channel | 通信内核内部的并行子流划分（`EPSignals::kNumMaxChannels=1280` 上限），用于提高带宽利用与交错同步（第 4 章）。 |
| PTX / SASS | NVIDIA 中间汇编 / 最终指令流；`common/ptx.cuh` 封装了 warp 原语、mbarrier、TMA、`red_add` 等（第 10 章）。 |
| 寄存器溢出（spill） | 寄存器不足导致落盘到 local memory；JIT 质量门 `EP_JIT_CHECK_NO_SPILLS`/`EP_JIT_CHECK_NO_LOCAL_MEMORY` 可拒绝此类内核（第 10/11 章）。 |
| copy engine（CE） | GPU 拷贝引擎：bucket all-gather 的纯 NVLink 路径由 CE 驱动（`num_sms=0`），见 `csrc/kernels/driver/`（第 9 章）。 |
| DeepJIT | 运行时 CUDA 内核编译框架：`std::format` 拼接模板 → nvcc → 缓存加载；入口在 `csrc/runtime/jit.hpp`（第 11 章）。 |

**框架与工程侧**

| 术语 | 释义 |
| --- | --- |
| BufferBase | 四大缓冲区的公共生命周期基类：构造参数 `explicitly_destroy`、`main_context`、`print_memory_usage`、`destroy`（第 3 章）。 |
| BufferAllocator | "先规划后落实"的分配器：`allocate()` 返回 meta 占位张量，`materialize()` 用单块连续 CUDA 存储的切片视图替换（第 3 章）。 |

| EventOverlap / EventHandle | 事件封装：`current_stream_wait()`、`wait()`、`register_hook_after_wait()` 等，支撑计算/通信重叠（第 10 章）。 |
| 通信流 | 进程级唯一的高优先级 CUDA 流 `get_comm_stream()`，所有通信内核在其上执行（第 10 章）。 |
| BucketSession | `with buffer.session():` 内允许集合通信接受未注册的外部张量，自动暂存（staging）到对称存储（第 9 章）。 |

| persistent_envs | 安装期烘焙进 `deep_ep/envs.py` 的默认环境变量（JIT 缓存目录、SL 等），导入时用户值优先（第 12 章）。 |

## 六、版本与事实基线

本文档的全部事实性断言都锚定在本仓库 docs-zh 分支的源码与 README 上，具体包括三类证据：其一是 README.md 与 README.zh-CN.md 中的接口说明、环境变量表、网络配置建议与版本发布说明；其二是 `csrc/` 与 `deep_ep/` 下源码文件中的函数签名、类定义、常量与逐行中文注释——仓库已为关键文件（如 `csrc/buffers/ep.hpp`、`deep_ep/buffers/ep.py`、`deep_ep/buffers/allocator.py`、`csrc/kernels/ep/dispatch.hpp`、`deep_ep/include/deep_ep/common/ptx.cuh` 等）补充了模块级中文注释块，本文对这些文件的描述与注释块保持一致；其三是 `tests/` 下的测试脚本所体现的行为约定。凡属于本文作者的分析、推导或与通用分布式系统知识的类比（例如第 1 章的通信量公式、第 6 章的 SM 估算模型推导、第 9 章的流水线重叠分析），均以"建模""推导""分析"等措辞明确标示，读者可以放心区分"仓库事实"与"文档论证"两类内容。

关于版本划分再强调一次：V1 时代的 DeepEP 曾把高吞吐（normal）与低延迟（low-latency）做成两套协议、两个接口，`figures/normal.png` 与 `figures/low-latency.png` 两张历史示意图即来源于那个时期；V2 用单一 `EPBuffer` 接口统一了两种场景，V2.5 进一步把统一后的 ElasticBuffer 拆分为四大缓冲区家族并引入 `BufferAllocator` 与专家负载均衡原语。本文档以 V2.5 为准绳，所有接口名、参数名、常量名均可在当前源码中逐一查证。

## 七、文档的两大目标与一个提醒

第一个目标是**建立心智模型**。读完 01 到 06 章后，读者应当在头脑中拥有一张完整的"运行时地图"：一次 dispatch 从 Python 的参数校验出发，经过 C++ 运行时的内核启动封装，落到 DeepJIT 编译出的设备内核，在专用通信流上以 notify warp 计数、槽位分配、NVLink/RDMA 两级搬运、mbarrier 通知的顺序完成，最终以句柄与事件的形式回到 Python。有了这张地图，任何性能问题都可以定位到"地图上的哪个环节"。

第二个目标是**提供可操作的工程判断力**。13 到 20 章的专题（性能调优实践、常见问题深挖、数值精度、确定性、系统对比、框架集成、容量规划、设计复盘）把前十二章的原理转变成"遇到什么问题查哪一章、调哪个参数、做哪个取舍"的实用指南。例如：SM 数与 QP 数何时该手动覆盖而非用估算默认值；`do_cpu_sync` 在训练与解码两个场景下的不同选择及其代价；`allow_multiple_reduction` 的精度与带宽交换如何量化；确定性模式的开关会影响什么、不会影响什么。

最后一个提醒：DeepEP 是一个仍在快速演进的系统，V2.5 的发布说明本身就列出了大量新特性与移除项。阅读本文档时若发现与最新源码不符之处，请以源码为准，并把本文的章节结构当作理解新变化的分析框架——分层的划分、约束的清单与设计原则的提炼，比任何具体参数值都更持久。

## 九、行文约定与阅读提示

最后说明三点行文约定，以避免阅读时的误读。第一，本文档区分三种内容强度：源码事实（函数签名、常量值、文件路径）以最高置信度呈现，均可在仓库中逐一核对；机制解释（"这段代码为什么这样写"）基于源码注释与结构推断，是文档的主体；定量建模（公式与数值估算）是作者的分析工具，用于揭示量级与权衡，其输出应视为规划参考而非精确预言。第二，文中的示例代码分两类：一类是直接摘自 README 或源码的片段（它们是行为契约），一类是为讲解而写的示意伪代码（它们标注了"示意"或出现在 ASCII 图中，不代表可运行的程序）。第三，文档中的章节交叉引用采用"第 N 章"或"第 N.M 节"的形式，术语表（第四节）提供定义锚点；遇到首次出现的名词拿不准时，先查术语表再继续，通常能省去回翻的时间。
