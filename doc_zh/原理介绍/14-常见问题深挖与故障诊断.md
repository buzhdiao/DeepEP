# 第 14 章 · 常见问题深挖与故障诊断

本章按"症状—根因—诊断路径"的结构，把使用 DeepEP 时最可能遇到的问题逐一深挖。每个问题的根因都指向前文论证过的机制，诊断手段全部来自仓库内已有的设施（环境变量、断言、超时与警告机制）。

## 14.1 初始化阶段的问题

**问题一：导入时报重复的 NCCL 库或版本不匹配。** 症状是 `deep_ep` 导入即失败，断言消息指出在当前系统中发现了重复的 NCCL 运行库（两个不同的 `libnccl` 路径），或运行库与链接库不一致。根因是第 12 章论证过的跨库句柄失效：DeepEP 的设备端通信域与窗口句柄绑定于**特定的 NCCL 共享库实例**，若 PyTorch 经自己的依赖加载了一份 NCCL、DeepEP 链接的是另一份，同一通信域在两份库里就是两个不相关的对象。诊断路径：`check_nccl_so()`（`deep_ep/__init__.py`）读取 `/proc/self/maps` 找出所有 `libnccl` 映射并比对，这一步的断言信息已经包含了两个冲突路径；修复方法是统一 NCCL 来源——用 `pip install "nvidia-nccl-cu13>=2.32.3" --no-deps` 安装单一版本，或设置 `EP_NCCL_ROOT_DIR` 指向与 PyTorch 加载一致的目录。`EP_SUPPRESS_NCCL_CHECK=1` 可以跳过检查，但 README 明确它"不会绕过 C++ 设备通信域的兼容性检查"，跳过检查只是把失败推迟到运行时，不解决问题。

**问题二：构造缓冲区时 NVLink 检查报警。** `check_nvlink_connections(group)` 在 EPBuffer 构造中被调用（第 3 章时序第 4 步），若节点内实际是 PCIe 互联而非 NVLink，此处会给出诊断。这类环境的正确应对不是忽略警告，而是确认组内拓扑：单节点通信若没有 NVLink，scale-up 路径的对称直达（`get_sym_ptr`）要么不可用要么退化，README 的环境要求（"节点内通信需要 NVLink"）在此被前置校验。判断依据可用 `get_physical_domain_size` 与 `get_logical_domain_size` 的返回值对照：两维不一致通常意味着实际连通性与预期划分不符。

**问题三：构造卡住或超时。** EPBuffer 构造的末尾是"双重同步 + 组屏障"（第 3 章第 9 步）。若某个 rank 没有加入组、或某 rank 的 CUDA 初始化失败，其余 rank 会卡在屏障上。构造参数 `num_cpu_timeout_secs`（默认 300）与 `num_gpu_timeout_secs`（默认 100）为此提供上限。诊断要点：确认所有 rank 使用了共享的 `MASTER_ADDR`/`MASTER_PORT`（`init_dist` 约定，第 12 章），确认没有 rank 在构造前崩溃退出；若使用容器环境，还要确认 NCCL 的网络探测（`ibstat`）在每个节点都能成功——README 指出 BucketBuffer 强制要求两路带宽可探测，EP 虽不强制但探测失败会直接影响解析式估算的输入。

## 14.2 运行阶段的同步类问题

**问题四：GPU 侧超时报错。** 所有设备端自旋等待统一走 `comm::timeout_while`，超时以 `num_gpu_timeout_secs` 换算的时钟周期为上限（`kNumOneSecCycles = 2000000000`，按 2 GHz 估算，第 10 章），屏障类错误还带有标签（`kDeviceBarrierTag`/`kKernelBarrierTag`）用于区分调用来源。超时的三大根因：其一，集合性被破坏——EP 的 dispatch/combine、EPLB 的两个原语、bucket 的集合通信都要求组内所有 rank 调用，某个 rank 缺席会让其余 rank 等待到超时；EPLB 尤其容易踩坑（"包括未被分配冗余槽位的 rank"都必须调用，第 7 章）。其二，路由表被提前修改——`topk_idx` 按引用存入句柄，若用户在句柄用完前改写了路由表，槽位解释错乱可能表现为计数器永不满。其三，真正的网络故障（链路 down、SL/VL 配置把流量黑洞化）。诊断顺序：先核对集合性（所有 rank 是否以相同参数调用），再核对句柄纪律，最后查网络层。

**问题五：CPU 同步挂起。** `do_cpu_sync=True` 时 CPU 会同步等待通信内核完成以读取接收计数（第 4 章）。挂起通常与 GPU 侧超时同根（问题四），但也可能是缓冲区复用违反了"替换前完成所有未完成操作"的纪律：若旧缓冲区的通信尚未结束就调用 `destroy()` 或创建新缓冲区挤占资源，可能出现资源竞争。README 的告诫"在替换其缓冲区之前，请先完成所有未完成的操作"配合 `BufferBase` 的显式销毁语义（构造时 `explicitly_destroy=True` 并手动调用 `destroy()`，第 3 章）是唯一正确的生命周期管理方式。忘记调用 `destroy()` 的直接证据是析构时的泄漏警告：C++ 侧 `destroy_on_destruction` 会打印"destroy() is not called before DeepEP … buffer destruction, which can leak resources"并立即 `fflush`（第 3 章）——看到这条警告应当当作 bug 修复，而不是噪声忽略。

**问题六：Session 相关断言失败。** `BucketSession` 的三处断言各有明确含义（第 9 章）：嵌套会话被拒（实例上仍挂着被替换的方法说明上次未正确退出）；多通信组被拒（`context_idx` 在会话内必须唯一）；结果未消费就被复用（暂存区游标在下次进入时清零）。其中第三类最难发现——症状不是报错而是数据错乱，因为暂存区被后续分配覆盖。修复方式是 README 示例注释的那句话："Consume or copy reduced_x before reusing the session storage"。

## 14.3 数据正确性类问题

**问题七：combine 结果数值异常。** 排查按依赖链倒序：第一，输入是否 BF16（README 硬约束，FP8 或 FP16 输入会触发断言或产生错误数值）；第二，`allow_multiple_reduction` 与构造配置是否与句柄生成时一致（第 5 章，配置漂移会让槽位解释错位）；第三，bias 张量的生命周期是否覆盖了 epilogue 的执行点——延迟 epilogue 模式下 bias 在 `current_stream_wait()` 时才被读取，若在此之前被释放或覆盖，结果会包含垃圾数据；第四，若为训练场景，确认反向传播使用了前向的同一 handle（第 5 章角色互换）。

**问题八：EPLB 梯度对不上。** 三个最常见的根因都写在 README 的纪律里：归约前未用本地贡献或零初始化 `expert_grads`（归约是累加语义，不清零也不覆盖，第 7 章）；前向与反向使用了不同的 `redundancy_mapping`（权重复制到哪里，梯度就要从哪里收回来，两表必须同源）；映射表中出现了"自己的专家放进自己的槽位"（README 禁忌，条目 `[r, c]` 指向 rank r 自己的专家会破坏"读对端"的假设）。附加检查：`redundancy_mapping` 是否为形状 `[num_nvlink_ranks, num_redundant_experts]` 的连续 CUDA int32 且域内每 rank 一致；专家编号是否用了 `owner_rank * num_local_experts + local_expert_idx` 的坐标；权重/梯度对是否满足"每专家字节数相同且为 `deep_ep.get_num_tma_alignment()`（32 字节）倍数"。

**问题九：FP8 dispatch 的 scale 相关错误。** FP8 模式下输入是二元组（`torch.float8_e4m3fn` 数据 + scale factor），TokenLayout 把 SF 与数据同槽随行（第 4 章）。常见错误包括：SF 的形状/打包数与 `num_sf_packs` 不匹配、未开启 `use_tma_aligned_col_major_sf` 而下游 GEMM 期望 TMA 对齐列主序、以及自制的量化函数与 `deep_ep/utils/math.py` 的 `per_token_cast_to_fp8`（基于 `torch.compile` 动态编译）语义不一致。数值校验可对照 `refs.py` 的参考 dispatch 与 `math.py` 的 `calc_diff`。

## 14.4 性能类"伪故障"

**问题十：首步通信异常慢。** 这几乎总是 JIT 首次编译（第 11 章）：分钟级的编译发生在第一次内核启动路径上。判据是慢只出现在第一次、且 `EP_JIT_PRINT_LOAD_TIME=1` 显示加载耗时巨大。修复是预热与多根缓存（第 13.7 节）。与之相伴的"伪故障"是滚动更新后的第一轮慢——配置变化（hidden、topk、rank 数）触发了新缓存条目，同样用预热解决。

**问题十一：吞吐远低于带宽预期。** 按第 13 章的检查清单逐项排除，最常见的四个根因依次是：SL/VL 未隔离导致拥塞波动、SM 搬运项成为瓶颈而 SM 数未校准、路由分布极端倾斜（通道饥饿，用 `cumulative_local_expert_recv_stats` 与 gate 生成器量化）、以及通道/QP 并发不足。注意区分"测量问题"与"真瓶颈"：未冲刷 L2 的基准（`flush_l2_cache` 缺失）会把上一轮的热缓存当作有效带宽。

**问题十二：解析估算与实测持续偏差。** 估算模型假设均衡门控（`get_theoretical_num_sms` 的 docstring 明示"This assumes a balanced gate distribution"）且带宽输入来自 `nvidia-smi`/`ibstat` 的静态解析。若集群的实际带宽与探测值偏差大，把实测值作为参数传入估算（第 13.1 节）即可校准；若门控分布显著不均衡，估算的方向性仍然正确（它决定的是 SM 预算的量级），但具体的流量分配应通过手动覆盖 SM 数微调。

## 14.5 诊断流程总图

把上述十二个问题收拢成一张决策路径图：

```text
异常发生
  ├─ 导入/构造期 → 14.1（NCCL 一致性 → NVLink 拓扑 → 构造屏障/超时）
  ├─ 同步类（超时/挂起/断言）→ 14.2（集合性 → 句柄与生命周期纪律 → 网络）
  ├─ 数值类 → 14.3（输入类型/配置一致性 → bias 生命周期 → EPLB 纪律 → FP8 SF）
  └─ 性能类 → 14.4（先排除 JIT 首编与测量偏差，再走 13 章清单）
```

三个贯穿性的诊断习惯值得强调：第一，`EP_BUFFER_DEBUG=1` 是第一响应工具，它输出的拓扑、缓冲区大小与 SM 估算构成了所有后续推理的数据底座；第二，断言消息要读完整——DeepEP 的宿主断言（`EP_HOST_ASSERT`，`common/exception.cuh` 的 `EPException`）与设备断言（`EP_DEVICE_ASSERT`）都会携带文件、行号与具体条件，多数问题的直接原因就写在断言文本里；第三，区分"必须修的错"与"必须管的警"——断言失败与超时报错是必须修的错，泄漏警告与 NVLink 检查提示是必须管的警，而 JIT 的缓存未命中日志只是信息。

## 14.6 本章小结

DeepEP 的故障面可以系统性收敛：初始化问题集中在 NCCL 一致性与拓扑校验（`check_nccl_so`、`check_nvlink_connections`）；同步问题的三大根因是集合性破坏、句柄/生命周期纪律违反、网络故障，由统一的两相位屏障与 `timeout_while` 超时机制兜底并带标签诊断；数据正确性问题沿着"输入类型 → 配置一致 → bias 生命周期 → EPLB 三纪律 → FP8 SF"的依赖链排查；性能类伪故障首查 JIT 首编与测量方法（`flush_l2_cache`），再走第 13 章清单。所有诊断都建立在仓库内已有的机制之上——环境变量、断言、超时与警告——不需要额外的观测设施即可完成大部分定位。

## 14.7 延伸讨论：一次完整排查的推演示例

为了把前六节的方法串起来，本节推演一个典型的故障场景（细节为示意，机制全部真实）。症状：多节点训练在第 47 层的 dispatch 偶发 GPU 侧超时报错，屏障标签指向内核内发起的等待（`kDeviceBarrierTag` 类诊断，第 10.3 节）。第一步，读断言全文——报错包含文件、行号与等待对象，确认是"等待某通道的到达计数"类条件（第 14.2 节问题四的三大根因排查开始）。第二步，核对集合性：该 EP 组共 64 rank，检查日志发现其中一个节点的四个 rank 在该步因数据加载异常提前抛出了 Python 异常——集合性破坏成立，这是根因。第三步，修复与预防：在数据加载处加错误传播（让异常在整个组一致失败），并把"组内任何 rank 异常即全体退出"纳入框架的容错策略。这个推演体现的第 14 章方法论是：超时是"果"，集合性破坏是"因"，报错标签与断言文本是连接两者的证据链。类似地，数值类症状（combine 结果错）的推演会沿 14.3 节依赖链走：先验证输入类型与配置一致（最便宜的检查），再验证 bias 生命周期（延迟 epilogue 的时序陷阱），最后才是内核级怀疑——绝大多数真实案例停在前两级。

## 14.8 延伸讨论：句柄与生命周期问题的静态防范

第 14.2 节的问题多与"纪律违反"有关，而纪律违反最适合用静态手段防范。本节给出一个可以在代码评审中使用的检查清单，每一条都对应一个已论证的机制。清单一：`EPHandle` 的持有时间是否覆盖其全部使用（训练循环中前向 handle 要活到 `dispatch_backward` 与 `combine_backward` 完成，第 5 章），且 `topk_idx` 在此期间只读（第 4 章不变式）。清单二：缓冲区的 `destroy()` 是否在所有在途操作之后（README"替换前完成所有未完成的操作"，第 3 章），且构造时 `explicitly_destroy=True` 的对象都有对应的显式销毁路径（析构泄漏警告，第 3 章）。清单三：会话块内是否消费或拷贝了结果（`BucketSession` 暂存区复用纪律，第 9 章），且没有嵌套会话。清单四：bias 与延迟 epilogue 结果的生命周期是否覆盖 `current_stream_wait` 的执行点（第 5.6 节）。清单五：EPLB 映射表与张量存储是否在交换完成前有效、前向反向是否同表（第 7 章）。清单六：`do_handle_copy` 是否保持默认 False（该参数保留兼容但必须为 False，第 4 章 docstring）。这六条都能用代码审查或静态检查工具落地（搜索 handle 的引用区间、destroy 的调用图、会话块的作用域），把运行时的同步类故障转化为开发期的检查项——这是第 14 章从"诊断"走向"预防"的收口。

## 14.9 延伸讨论：集合性问题的组织级防范

集合性（组内所有 rank 以一致参数调用）是 DeepEP 一切集合原语的前提（第 7.5 节），但它的破坏往往源于组织层面的疏漏而非单个 bug。本节给出组织级的三道防线。第一道是**调用图的一致性审计**：确保组内所有 rank 走的是同一段代码路径（同一函数、同一分支条件），最危险的模式是"条件调用"——某 rank 因本地条件（数据为空、配置开关）跳过了调用，而其他 rank 进入了集合等待；防范是把这些条件改为"全组一致的输入"（例如空数据也调用、传空映射表，第 7.8 节退化情形）。第二道是**参数一致性的断言前移**：`num_max_tokens_per_rank`、`expert_alignment`、构造参数这些"必须全组一致"的量（第 3、4 章），应在构造时通过 all-gather 元信息比对（框架层职责），而不是等内核断言在运行时报错。第三道是**故障传播的全局化**：任何一个 rank 的本地异常都应升级为全组一致的失败（第 14.7 节推演的修复），避免"部分 rank 继续、部分 rank 消失"造成的等待悬空。三道防线的共同哲学与第 20.4 节一致：**把不确定性与不一致性消灭在运行时之前**——集合性问题在组织层预防的成本，比在内核层诊断的成本低两个数量级。

## 14.10 延伸讨论：性能问题的分层归因法

第 14.4 节把性能类问题列为"伪故障"与真瓶颈，本节给出一个分层的归因顺序，确保每次性能调查都从最便宜、最可能的层开始。第一层是**测量方法层**：确认计时方式（CUDA 事件与 `bench` 的预热均值，第 12 章）、缓存冲刷（`flush_l2_cache`）、剖析开关的固定（`EP_USE_NVIDIA_TOOLS` 等）——这一层的偏差可以造成数倍的假象。第二层是**编译与预热层**：JIT 首编译、缓存未命中、质量门是否开启（第 11 章）——次轮与首轮差异巨大时先查这里。第三层是**网络配置层**：SL/VL 隔离、自适应路由、PCI 原子模式、探测值对校准值的比值（第 6、13 章）——网络打折是"带宽远低预期"的最常见真因。第四层是**资源预算层**：SM 数是否与批次规模匹配（第 13.2 节两条准则）、QP 是否被通道吃满、通道是否饥饿（第 4.10 节）。第五层才是**内核与协议层**：到达模式、归约布局、chunk 流水——只有在排除前四层后才值得怀疑，因为它们经过最多的验证（测试体系，第 12 章）。这个顺序的本质是按"先环境后代码、先全局后局部、先便宜后昂贵"排列假设检验——与第 14 章开头的三分法（同步、数值、性能）配合，构成完整的排障方法论。

## 14.11 延伸讨论：可观测性的最小配置

DeepEP 自带的可观测面足以支撑大部分定位，本节给出"最小可观测配置"的建议清单。常备开启项：`EP_BUFFER_DEBUG=1` 用于每次部署验收（打印拓扑、缓冲区大小与 SM 估算，验证第 19 章规划），验收后可关闭以省日志。剖析期开启项：`EP_JIT_WITH_LINEINFO=1`（内核剖析定位到源码行，第 11 章）、`EP_USE_NVIDIA_TOOLS=1`（外接 Nsight 时的占位豁免，README）。排障期按需项：`EP_JIT_DEBUG=1` 与 `EP_JIT_PRINT_COMPILER_COMMAND=1`（编译类问题）、`EP_JIT_PRINT_LOAD_TIME=1`（预热覆盖率验证）、`EP_GIN_GDAKI_DEBUG=1`（Gin 设备侧深查，第 11 章）。运行期常备但免配置项：构造与析构的泄漏警告（`destroy_on_destruction` 的 printf，第 3 章）、断言的文件行号（`EPException`，第 10 章）、超时的屏障标签（第 10.3 节）——它们无需开关，出问题时会自动出现，因此团队要把"看到警告就登记"写成惯例（第 14.2 节问题五的教训）。这套配置的总成本近零（全是环境变量），而它覆盖的信息面——拓扑、资源、编译、同步、数值断言——恰好对应第 14 章四类问题的诊断入口。最后提醒一条边界：可观测配置不改变通信行为（README 明确剖析开关"不影响生产环境通信"），因此可以放心在验收与剖析之外保持默认关闭。

## 14.12 延伸讨论：注入式自检——主动制造故障来验证防御

排障方法论通常假设"故障先发生、排查后跟上"，本节介绍一个反向的实践：在部署验收阶段主动注入故障，验证系统的防御与诊断面是否如预期工作。注入的用意不是破坏，而是把第 14 章的诊断链在"有准备的条件下"走一遍——真故障发生时的排障速度取决于团队对诊断信号的熟悉程度，注入演练是最好的熟悉方式。可注入的场景与其验证目标：其一，单 rank 迟到（延迟一个 rank 的启动），验证构造屏障的行为与报错信息是否指向"哪个 rank 未到"（第 14.1 节问题三、第 3 章双重同步）；其二，单 rank 集合调用缺席（跳过一次 dispatch），验证 GPU 超时的报错标签与等待条件（第 14.2 节问题四、第 10.13 节超时分层）；其三，`destroy()` 漏调，验证析构泄漏警告的输出与 `fflush`（第 3 章、第 14.2 节问题五）；其四，NCCL 双库环境（加载一个不同版本的 `libnccl`），验证 `check_nccl_so` 的断言（第 14.1 节问题一）；其五，错误的 `expert_alignment` 与映射表（EPLB 自复制条目），验证构造与内核的断言拒绝（第 14.3 节问题八）。演练的产出是"每个注入场景的标准响应时间"——它既是团队排障能力的度量，也是第 14.9 节组织级防线有效性的验收。注入演练应安排在每次大版本升级后的验收窗口，与第 13.7 节的 JIT 预热、第 19.6 节的基准闭环一起构成部署验收的三件套。

## 14.13 延伸讨论：把排查经验沉淀为部署验收清单

本章的最后收口是把所有"事后排查"转化为"事前验收"。验收清单的组织方式按部署的生命周期分四段。安装段：NCCL 版本与唯一性（`check_nccl_so` 通过，第 12.2 节）、DeepJIT 子模块与缓存目录就绪（`EP_JIT_CACHE_DIR` 可写且多根配置正确，第 11.5 节）、`persistent_envs` 的烘焙值与集群约定一致（第 12.1 节）。拓扑段：NVLink 连通性通过（`check_nvlink_connections` 无诊断，第 3 章）、带宽探测可用且探测值记录在案（`nvidia-smi` 与 `ibstat`，第 6.10 节）、规模断言核对（rank 数与专家数在 `kNumMaxRanks`/`kNumMaxExperts` 安全区内，第 6.11 节）。构造段：`EP_BUFFER_DEBUG=1` 的输出与容量手册一致（第 19.12 节）、QP 预分配数与原子能力匹配（65/129/17 的来源，第 6.3 节）、LB 区域与 Engram 的规划落实无断言（第 3.6 节）。运行段：预热覆盖率验证（`EP_JIT_PRINT_LOAD_TIME` 全部近零，第 11.10 节）、参考实现对照通过（`calc_diff` 在容差内，第 12.3 节）、重叠配方的微观分解符合预期（第 13.12 节）、第 14.12 节的注入演练全部通过。四段清单的总条目在二十条上下，全部由仓库内机制支撑——它的价值是把本章的"十二个问题"从"发生了再查"变成"部署时逐条打钩"，这也是故障诊断章的最终形态：最好的诊断是不需要诊断。

## 14.14 延伸讨论：排障中的信息经济学

排障的效率差异往往不在方法而在"第一小时抓了什么信息"，本节给出按获取成本排序的信息采集顺序——先抓便宜且信息量大的，贵的留到必要时刻。成本近零、信息量大的一档：报错全文（断言的文件、行号、条件与屏障标签，第 10 章）、`EP_BUFFER_DEBUG` 的构造期输出（拓扑、容量、SM 估算，第 13.1 节）、以及故障时刻的配置快照（构造参数、环境变量）——三者都已在磁盘或日志里，采集只是收集。成本中等的一档：复现实验（受控负载的最小复现，第 14.7 节推演的第一步）、剖析时间线（`bench_kineto` 的内核级分解，第 12 章）、JIT 缓存清点（实例名与版本关联，第 11.13 节）——需要一次受控运行，但能给出方向性结论。成本高昂的一档：跨节点协同抓取（各 rank 同时段的日志对齐）、网络侧抓包与交换机计数器、内核级调试（Nsight 深查）——只在中等档指向网络或内核时才启动。采集顺序背后的原则与第 14.10 节分层归因法同构：**信息的边际价值随获取成本递减，先建立方向再投入深度工具**。实践中最常见的浪费是"跳过便宜档直接抓包"——网络抓包能确认链路问题却无法回答"为什么只有这层慢"，而便宜档的配置快照往往一行就锁定根因（例如 `allow_multiple_reduction` 与句柄生成时不一致）。把本节的顺序写进团队的排障手册，与第 14.13 节验收清单、第 14.12 节注入演练并列，构成故障工程学的完整三件套：事前预防、事中演练、事后有序。
