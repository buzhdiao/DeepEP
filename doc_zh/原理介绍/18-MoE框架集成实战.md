# 第 18 章 · MoE 框架集成实战：从 README 示例到完整训练循环

本章把 README"接口与示例"部分的代码逐段解读，并把它扩展成一次完整训练循环的集成蓝图。目标读者是在自己的训练/推理框架中接入 DeepEP 的工程师；每一节的建议都对应前文论证过的机制。

## 18.1 缓冲区的获取与复用：全局单例模式

README 的第一个示例定义了缓冲区管理的标准形态：模块级全局变量 `_buffer` 与 `_num_comm_sms`，配一个 `get_buffer(group, num_max_tokens_per_rank, hidden, num_topk, use_fp8_dispatch)` 工厂函数。其核心逻辑值得逐行解读：

```python
required_bytes = EPBuffer.get_buffer_size_hint(
    group, num_max_tokens_per_rank, hidden,
    num_topk=num_topk, use_fp8_dispatch=use_fp8_dispatch,
)
if _buffer is not None and _buffer.group == group and _buffer.num_bytes >= required_bytes:
    _num_comm_sms = _buffer.get_theoretical_num_sms(num_experts, num_topk)
    return _buffer
```

三个要点：其一，复用判断的三个条件（同一进程组、容量足够）来自第 3 章"缓冲区大小与瞬时批次无关、按容量上限分配"的性质——只要容量覆盖新配置，旧缓冲区无需重建；`get_buffer_size_hint` 在不构造的情况下完成预判。其二，复用时仍要刷新 SM 估算（`get_theoretical_num_sms`），因为专家数与 topk 变了而缓冲区没变，SM 预算是随配置变化的。其三，"在替换其缓冲区之前，请先完成所有未完成的操作"（README）——重建缓冲区前必须确保旧缓冲区上没有在途通信（第 14 章问题五）。这个模式适用于绝大多数框架：**每个 EP 组一个缓冲区、按容量复用、配置变化时才重建**。

## 18.2 前向的四个辅助函数：语义映射

README 的训练示例给出四个辅助函数，它们的命名本身就在传递第 5 章的反向语义：

`dispatch_forward` 接收 `(x, topk_idx, topk_weights)`，调用 `_buffer.dispatch(...)`，关键参数组合是 `do_expand=True`、`do_zero_padding=True`、`use_tma_aligned_col_major_sf=True`、`defer_epilogue=True`、`async_with_compute_stream=True`、`allocate_on_comm_stream=previous_event is not None`、`do_cpu_sync=do_cpu_sync`。这组参数的每个成员都在前文出现过：展开布局与零填充服务分组 GEMM（第 4 章）、TMA 对齐 SF 服务下游量化 GEMM（第 15 章）、延迟 epilogue 与异步开关构成重叠配方 B 的骨架（第 13.5 节）、CPU 同步按场景开关。

`combine_forward` 用前向的 handle 调 `combine`，`bias` 参数在此处注入共享专家输出或残差（第 5 章）。`dispatch_backward` 的实现体就是一次 `combine`（传入 `grad_recv_topk_weights` 作为乘法因子）——函数名与实现体的反差正是"反向的 dispatch 是 combine"的代码化。`combine_backward` 反之。这四个函数合起来定义了 MoE 层的完整数据面；框架只需在门控、专家 GEMM 与优化器三处挂接。

## 18.3 重叠时序：从示例到模板

README 的重叠片段："先发起通信，并在专家计算需要其结果的位置等待"：

```python
event = dispatch_forward(...)
# ... do some independent computation here ...
recv_x, _, recv_topk_weights, handle = event.current_stream_wait()
# ... run the expert GEMMs and apply recv_topk_weights ...
event = combine_forward(expert_output, handle)
# ... do some independent computation here ...
combined_x, _ = event.current_stream_wait()
```

把这段扩展成单层 MoE 的完整时序模板（训练路径，含共享专家与 EPLB）：

```text
门控(gate) ──▶ 规划/映射(EPLB, CPU/GPU) ──▶ lb_prefetch_weights(事件P)
   │                                              │
   │            ┌─────────── 独立计算（共享专家前向、bias 准备）──┐
   ▼            ▼                                              │
dispatch_forward(previous_event=就绪事件) ──▶ 事件D            │
   │                                                          │
   └─▶ current_stream_wait(D)：展开输出 + handle               │
        专家 GEMM（用 recv_topk_weights 乘上）                 │
        combine_forward(expert_output, handle, bias) ──▶ 事件C │
        current_stream_wait(C)：combined_x ──▶ 层输出          │
        【反向】…… 专家 GEMM 反向、lb_reduce_grads(事件G) ……   │
        dispatch_backward = combine(grad_y, handle, …)         │
        combine_backward  = dispatch(grad_combined_x, handle) ─┘
```

模板中的每个等待点（`current_stream_wait`）都应放在"消费者真正需要数据"的位置，中间填满独立计算——这是第 10 章事件模型的全部意义。两个工程细节容易出错：`capture()` 必须在独立计算入队**之前**调用（捕获的是"输入就绪"事件，第 10 章）；延迟 epilogue 的返回值由第一次等待产生，必须保留（README："返回的结果由第一次等待产生，因此请保留它供后续计算使用"）。

## 18.4 训练与解码的分支策略

同一套辅助函数要服务训练、prefill 与 decode 三种负载，分支点有两个：

**CPU 同步分支**。README 对此有明确指示："`do_cpu_sync=True` 用于获取精确的输出尺寸和 CPU 侧的专家计数，常用于训练和 prefill。当使用 GPU 侧的接收计数时（如解码场景），将其设为 `False`：此时输出会按配置的容量分配，专家 GEMM 必须使用 `handle.psum_num_recv_tokens_per_expert` 来确定有效的专家范围。"训练/prefill 用精确尺寸换取一次同步（可接受，因为批次大、同步占比小）；decode 用容量分配 + GPU 计数避免任何主机等待（第 13.5 节配方 B）。

**句柄复用分支**。decode 的多步生成若路由不变（缓存命中），README 指出可以复用 handle："缓存的 dispatch 会重放已保存的展开布局，而无需再做一次接收计数的 CPU 同步。在该句柄的所有使用完成之前，请保持原始 `topk_idx` 不变。"同时强调边界："新的路由决策需要一次全新的 dispatch；仅靠解码并不会使旧的路由句柄变为可复用。"集成方的实现要点是为 handle 维护与路由缓存一致的生命周期（与 KV 缓存的命中判断同一时机失效）。

**容量分支**。`num_max_tokens_per_rank` 必须覆盖三种负载的公共上限（第 18.1 节），decode 的容量浪费由容量分配的输出缓冲承担——这是"公共容量"设计的固有代价，换来的是单缓冲区服务全部场景（避免重建）。

## 18.5 与专家 GEMM 的对接

集成中最需要跨库协调的是专家 GEMM 的布局要求：README 明示"`expert_alignment` 设置为分组 GEMM 的 token 对齐量；对于 DeepGEMM，请使用 `deep_gemm.get_mk_alignment_for_contiguous_layout()`"。展开式布局（`do_expand=True`）的输出恰好是"每专家连续区间"的形态，与连续布局的分组 GEMM 直接对接；区间边界由 `handle.psum_num_recv_tokens_per_expert` 前缀和给出（训练精确模式）或由该前缀和界定有效范围（解码容量模式）。两个细节：展开式下的 `recv_topk_weights` 是一维的、"每个专家行对应一个值"（README），专家计算在 combine 之前把它乘上；`do_zero_padding=True` 只清零对齐空隙，在无 CPU 同步模式下"并不会使未使用的输出容量变成有效数据"——GEMM 仍须按前缀和裁剪，不要把容量当作长度。

## 18.6 集成检查单

把本章收拢为接入时的检查单：第一，缓冲区管理用全局单例 + `get_buffer_size_hint` 复用判断（18.1）；第二，四个辅助函数按 18.2 的参数组合落地，反向语义记住"名实互换"；第三，重叠时序按 18.3 模板，等待点紧跟消费者，`capture` 与首次等待的纪律牢记；第四，训练/prefill 与 decode 分别用配方 A/B（18.4），handle 生命周期与路由缓存对齐；第五，GEMM 对齐用 `expert_alignment` 接通 DeepGEMM，有效范围永远以前缀和为准（18.5）；第六，EPLB 若启用，按第 7 章纪律（同表、集合性、初始化与不清零）接入规划器；第七，确定性需求按第 16 章配方分级；第八，故障排查按第 14 章依赖链。完成这八步，一个 MoE 框架与 DeepEP 的集成在功能与工程两个维度上都站住了。

## 18.7 本章小结

README 的示例代码实际上是"最小正确集成"的完整样板：全局单例缓冲区管理、四个名实互换的辅助函数、三段式重叠时序、训练与解码的分支策略、与 DeepGEMM 的对齐对接。本章把这些要点重组为可复用的模板与检查单，并明确指出三个最易出错的细节——`capture` 的时机、首次等待结果的保留、有效范围与前缀和的绑定。集成的本质是把前文的机制纪律翻译成框架代码：遵守第 4 章的句柄不变式、第 5 章的角色互换、第 10 章的事件模型与第 7 章的 EPLB 纪律，就没有需要"碰运气"的灰色地带。

## 18.8 延伸讨论：推理服务集成的特殊考量

第 18 章主体面向训练循环，推理服务（尤其在线 decode）的集成有几个特殊考量值得单独讨论。第一是**时延目标的位移**：训练关心吞吐（层时间被重叠吸收），在线 decode 关心尾延迟（单步时间直接是用户可感知的指标）——因此重叠配方的选择从"最大化重叠"转为"消除 CPU 介入"：配方 B 的零 CPU 同步、句柄复用（免计数同步，第 18.4 节）、以及把 JIT 预热与缓冲区复用做到部署期完成（运行期零重建，第 13.10 节）。第二是**批次的动态性**：在线负载的 token 数剧烈波动，而 `num_max_tokens_per_rank` 是构造期冻结的公共容量（第 3、18.4 节）——容量按峰值预留的显存代价在推理服务里由"多实例分摊"或"混合部署的统一容量"承担，第 19.10 节会讨论混部策略。第三是**路由缓存的失效联动**：decode 的句柄复用依赖路由不变（第 4 章不变式），在线服务里路由缓存与 KV 缓存的命中判断必须使用同一判定时机（同一请求的前缀、同一投机解码的草稿验证结果）——两者失效不同步会造成"用了旧路由的 KV"类错位（第 8.11 节 KV 传输与 Engram 的关系也在此交汇）。第四是**失败语义**：在线服务不能像训练那样整组重启（第 14.7 节），超时与失败的处置要接入服务框架的请求级重试与降级，DeepEP 的超时机制（第 10.13 节）提供了失败信号的上界。这四条考量合起来，构成推理侧集成与训练侧集成的差异面——共享的是第 18.2 节的四个辅助函数，不同的是围绕它们的工程策略。

## 18.9 延伸讨论：多 EP 组与多模型共存

一个进程内多个缓冲区（第 3.11 节资源账）在框架集成中的典型形态是"多个 EP 组共存"：模型的不同模块用不同 EP 度、或张量并行与专家并行混合时的多个通信组。集成要点有三。其一，**组的身份管理**：`get_buffer` 的复用判断以进程组为键（第 18.1 节），多组时用"组到缓冲区"的映射表而非单一全局变量；不同组的 `num_max_tokens_per_rank` 可以不同，但同组内必须一致（第 3 章）。其二，**通信流的时间轴**：所有组共享进程级通信流（第 10.11 节推论），组间的通信天然串行——若两个组必须真并行（例如不同模型实例），用多进程而非单进程多组（第 10.11 节、第 12 章多节点约定）。其三，**显存与 QP 的总账**：组数乘以各自的五项显存分解（第 19.3 节）与 QP 预分配（第 3.11 节第二笔账）必须落在预算内；多组共存是"QP 总量上限"最常见的触发场景。另外，`deep_ep/comm` 模块的 `destroy_all_managed_nccl_comm()`（第 12 章）在多组共存时的用途是退出前的统一清理——与各缓冲区显式 `destroy()` 的顺序纪律（先组内、后全局）配合使用。多组共存本身没有协议难点，难点全在资源账与生命周期秩序——这再次印证第 20.4 节"成本放在构造期"的设计：只要构造期把账算清，运行期的多组只是查表。

## 18.10 延伸讨论：缓冲区重建时机与训练循环的生命周期

第 18.1 节的复用判断在训练循环中有一个隐含前提：重建只发生在"安全点"。本节把训练循环的生命周期与缓冲区重建的交互讲清。安全点的定义来自第 3 章"替换前完成所有未完成的操作"——即该 EP 组上没有在途的 dispatch/combine/EPLB 操作（所有 `EventOverlap` 已等待、所有 handle 已用尽）。训练循环中的自然安全点是：数据集切换边界、评估阶段开始前、以及显式的设计变更点（改 EP 度、改容量）。非安全点的典型反例是梯度累积循环的中间：上一个 micro-batch 的反向（`dispatch_backward`/`combine_backward`）可能尚未消费完 handle，此时重建会悬空在途资源。实现上，框架应在重建前插入一个"排空点"：等待该组所有事件（对每个在途 `EventOverlap` 调 `wait`，第 10 章）并确认无引用残留，然后按第 14 章清单二检查销毁路径。另一个相关问题是**重建的广播**：重建决策（容量变化）发生在某个 rank 的调度逻辑里，但构造必须全组同步进行（构造末尾的组屏障，第 3.4 节）——因此"要重建"这个决策本身需要一次组间通信（框架层的 all-gather 布尔量）来保证同时性。把这两个机制（排空点、重建广播）写进框架的缓冲区管理器，第 18.1 节的单例模式就从"示例级"升级为"生产级"。

## 18.11 延伸讨论：与梯度累积和优化器的联动

训练集成的最后一环是梯度累积与优化器的联动，DeepEP 的数值纪律（第 15 章）在此有几个落点。梯度累积场景：多个 micro-batch 的梯度在优化器步骤前累加——EPLB 的 `lb_reduce_grads` 是累加语义（不清零，第 7 章），天然支持跨 micro-batch 累加，集成方只需在优化器步骤后按第 7 章纪律清零冗余梯度；主缓冲区的 dispatch/combine 每个 micro-batch 独立（无跨批状态，槽位按批次重建），不引入累积约束。优化器联动：`lb_reduce_grads` 的输出（属主 `expert_grads`）直接对接优化器的梯度视图——要求"每专家一行"的展平布局（第 7 章），框架的参数分组若按专家切分，展平视图与优化器状态的对应关系要在集成时一次对齐（这是认知维度成本的一处集中点，第 17.10 节）。混合精度联动：第 15.4 节的数值链表明激活链的 BF16 误差与梯度链的 FP32 精度是两条独立通道，优化器的 master weight 机制不受通信层影响——通信库的责任边界止于"不引入额外误差源"。还有一处容易被忽略：`cumulative_local_expert_recv_stats` 是**累计**计数（第 4 章），对接 EPLB 规划器时应做差分得到每步分布，而不是直接用累计值——这个细节在第 7.8 节的收益模型与第 16 章的种子链里都隐含出现，集成时落实为一句代码，却决定了负载监控的正确性。

## 18.12 延伸讨论：端到端联调的推荐顺序

作为集成章的收口，本节给出从零到生产的联调顺序，每一步都以前文的机制为验收标准。第一步，单节点单卡冒烟：最小配置构造 `EPBuffer`（小容量），跑一次 dispatch/combine 对照 `refs.py`（第 12 章三件套）——验收构造流程与数值基线；`EP_BUFFER_DEBUG=1` 全程开启（第 14.11 节）。第二步，单节点多卡：验证 NVLink 直达路径与对称内存（`get_sym_ptr` 语义，第 3 章），观察通道化行为（第 4.10 节）。第三步，多节点：按第 12.10 节的组织纪律启动，验证 hybrid 两级路由与 QP 并发（第 6 章）。第四步，重叠配方切换：按第 13.5 节三配方逐个验证，用 `bench_kineto` 确认重叠成立（第 13.12 节的微观分解）。第五步，专项原语逐个接入：EPLB（第 7 章纪律）、Engram 或 PP 或 Bucket（按需，第 8、9 章），每个原语都对照第 13.14 节的速查表。第六步，确定性与容量规划：按第 16.5 节配方分级接入，按第 19 章完成容量手册。第七步，生产灰度：JIT 缓存预热（第 11.10 节）、网络配置清单复核（第 19.4 节）、第 14.8 节静态检查单过一遍。七步顺序的原则是"每一步都建立在上一步的验收之上"——与 DeepEP 自身的分层（第 2 章）同构：集成调试也应当沿依赖方向进行，而不是直接在多节点生产配置上试错。

## 18.13 延伸讨论：从联调到回归的自动化

第 18.12 节的七步联调是一次性的，本节讨论如何把其中的可重复部分固化为自动化回归，使集成质量随代码演进保持。可自动化资产分三类。第一类，**功能回归**：第 12 章测试的精简子集（`test_ep` 的参考对照、`test_allocation` 的规划器契约、按需的专项原语测试）接入持续集成，触发条件按第 15.15 节原则三（内核、格式、量化、布局变更）。第二类，**时序回归**：重叠配方的微观分解（第 13.12 节）固化为基准脚本——记录 dispatch 的排队、执行、epilogue 三段的耗时分布，超过阈值即告警（探测通信被打断的回归，如某次框架改动意外引入了 CPU 同步）。第三类，**契约回归**：第 14.8 节的六条静态检查单以代码检查工具落地（handle 引用区间分析、destroy 调用图、会话作用域），加上第 16.13 节的位级复现验收脚本（若启用第三层确定性）。三类资产的共同特征是都建立在"仓库内机制"之上（测试体系、剖析工具、断言与警告），不需要额外观测设施——与第 14.11 节最小可观测配置呼应。自动化的边界也要诚实：覆盖不了的部分（真实集群的网络波动、长训练的累积效应）留给灰度与巡检（第 14.13 节运行段）。本节的收口呼应第 18 章开头的目标：集成不是"接上就能跑"，而是"接上之后，每一次演进都有回归网兜住"——这正是把原理章（第 3 到 11 章）的纪律转化为工程资产的最后一里路。

## 18.14 延伸讨论：集成代码的形态演进

集成不是一次性写完的——随框架演进，集成代码本身会经历三个形态阶段，本节描述各阶段的特征与升级时机。阶段一，**直调期**：按第 18.2 节模板直接调用，四个辅助函数内联在模型代码里——适合验证期，特征是简单直接，代价是模型代码与通信细节耦合。阶段二，**封装期**：辅助函数与缓冲区管理（第 18.1 节单例）收敛为一个"通信适配层"模块，模型代码只依赖适配层接口——升级时机是第一个非默认配置需求出现时（例如训练与推理共用一套辅助函数但配方不同，第 13.5 节），封装让差异收敛在模块内。阶段三，**治理期**：适配层之上出现策略组件——缓冲区管理器（重建时机与全组广播，第 18.10 节）、负载监控器（`cumulative_local_expert_recv_stats` 的差分接入，第 18.11 节）、确定性配置器（第 16.12 节分层目标）——升级时机是多模型或多租户共存（第 18.9 节）时，策略需要跨适配层共享。三个形态没有优劣，只有匹配：形态一匹配原型验证、形态二匹配单一产品、形态三匹配平台化部署。判断自己所处形态的信号很直接：当第 14.8 节静态检查单开始反复发现同类问题时（句柄跨步泄漏、重建时机随意、会话结果未消费），就是向上一个形态升级的时机——集成代码的演进由"问题的重复出现"驱动，而不是由架构审美驱动。本节与第 18.13 节的回归自动化衔接：形态越往上，回归网就应该越密——形态三的治理组件正是第 18.13 节三类回归资产的宿主，而回归资产的密度又决定了形态升级的胆量：网够密，才敢重构。

## 18.14 延伸讨论：与数据加载和调度器的协同陷阱

集成的问题不一定出在通信代码里——与数据加载、调度器协同的边界处有四个高频陷阱，本节逐个识别并给出规避。陷阱一，**数据加载异常导致的集合性破坏**（第 14.9 节）：加载器在某 rank 抛异常后跳过该步的 dispatch，其他 rank 进入集合等待——规避是把"加载成功与否"提升为全组一致的输入（异常也要参与集合：传递标志位再一致失败），并让加载错误触发全局退出而非本地跳过。陷阱二，**动态 batch 与公共容量的冲突**：调度器为提升吞吐动态拼批，批次超过 `num_max_tokens_per_rank` 时触发容量断言——规避是把容量约束下推到调度器的拼批策略（上限作为硬约束传入调度器，而不是等断言在通信层报错，第 18.4 节公共容量的调度器侧表述）。陷阱三，**步间状态与句柄生命周期的错位**：调度器把"步"作为恢复与缓存失效的粒度，而 handle 的生命周期跨步（前向 handle 活到反向完成，第 5 章）——规避是在框架的步边界定义中把"handle 全部用尽"作为步完成的判据之一，而不是按优化器步骤粗粒度清理。陷阱四，**混合并行中的拓扑假设**：调度器假设所有通信组拓扑一致（同为 NVLink 域或同为 RDMA 域），而 PP 要求纯 RDMA 组、EPLB 要求单 NVLink 域（第 12 章测试前提）——规避是在构建各通信组时按用途选择组划分（第 18.9 节多组管理），并在调度器的组注册表中记录每组拓扑以供断言。四个陷阱的共同模式是"边界职责未定义"——本节的回答与第 18.10 节重建时机、第 18.11 节优化器联动一起，构成集成边界职责的完整清单：数据、调度、缓冲区、梯度四条边界，每条都要有明确的契约与验证。
